## Summary

This is a 10-commit dependency-refresh phase. Nine of the 10 commits are real major-version bumps with concrete breaking changes the planner must thread into each atomic unit. **One commit (drizzle pair) and one commit (better-auth) are nearly no-op patches under a strict "latest stable" reading** — they were added to scope on 2026-05-11 when the user pushed back on the "out of scope" classification, but verification on the npm registry on 2026-05-11 shows `drizzle-orm@latest = 0.45.2` (current pin), `drizzle-kit@latest = 0.31.10` (current is `^0.31.0` — patch refresh only), `better-auth@latest = 1.6.10` (current is `1.6.9` — single patch). The planner should flag this to the user in the PR body so the expectation matches reality.

Of the eight real major bumps, **three carry CONTEXT.md "special vigilance" status (D-07)** — pino 10, dotenv 17, better-auth — and each has a verified-low-risk path: pino 10's only breaking change is dropping Node 18 (we're on 22); dotenv 17 introduces an advertising log line on boot that the bump MUST suppress with `{ quiet: true }`; better-auth has no major release on `latest` (RFC stays on 1.6.10).

**The riskiest commit is TypeScript 6** — the largest set of breaking changes since TS 2.0. The single most impactful change is the `types` compilerOption defaulting to `[]` (was: load-all-from-`node_modules/@types`) — this WILL break the current tsconfig.json unless `"types": ["node", "vitest/globals"]` is made explicit (it already is). The current tsconfig is already 100% TS 6-compatible — the planner can land TS 6 with zero tsconfig changes IF the @typescript-eslint v8 peer holds (it does: peer is `typescript: ">=4.8.4 <6.1.0"`, so TS 6.0.x is compatible; TS 6.1+ would break, which is a future-phase concern, not this phase's).

**The most ambiguous commit is ESLint core family** — ESLint 10 adds three new rules to `eslint:recommended` (`no-unassigned-vars`, `no-useless-assignment`, `preserve-caught-error`), enforces flat-config `name` property, and removes deprecated context APIs that our internal `eslint-plugin-tenant-scope` may use. The planner MUST audit `eslint-plugin-tenant-scope/index.js` for `context.getCwd()` / `context.getFilename()` / `context.getSourceCode()` / `context.parserOptions` / `context.parserPath` and replace with the new property accessors before the bump.

**Two commits are effectively no-ops at the code level:**
- `@types/supertest` 7 → there are ZERO `import supertest` references anywhere in the codebase (grep result: 0 in `src/`, 0 in `tests/`). Both `supertest` and `@types/supertest` are stranded dependencies from earlier phases. The bump is a package.json version change with no code surface.

#### Commit 1 — ESLint core family (eslint 9→10, @eslint/js 9→10, eslint-config-prettier 9→10, globals 15→17)

**Breaking changes (sourced from [ESLint v10 migration guide](https://eslint.org/docs/latest/use/migrate-to-10.0.0) and [v10 release notes](https://github.com/eslint/eslint/releases)):**
- `eslint:recommended` adds three new rules: `no-unassigned-vars`, `no-useless-assignment`, `preserve-caught-error`. These WILL fire in this codebase unless pre-vetted.
- Flat-config `name` property is now expected (recommended, not strictly required for user configs — but `@eslint/js`'s shipped configs now include a `name`, so the layout is conventional).
- Deprecated context APIs REMOVED from rule context: `context.getCwd()`, `context.getFilename()`, `context.getPhysicalFilename()`, `context.getSourceCode()`, `context.parserOptions`, `context.parserPath`. Replace with property accessors (`context.cwd`, `context.filename`, `context.physicalFilename`, `context.sourceCode`, `context.languageOptions`).
- Deprecated SourceCode methods REMOVED: `getTokenOrCommentBefore()`, `getTokenOrCommentAfter()`, `isSpaceBetweenTokens()`, `getJSDocComment()`.
- `eslint-env` comments are now errors (none in this repo — verified).
- Node.js requirement: `^20.19.0 || ^22.13.0 || >=24` — we're on Node 22.12+, so within range only if our local/CI is ≥ 22.13. **CI uses `node-version: 22` (auto-resolves to latest 22.x).** Local engine pin is `>=22.12` — bump to `>=22.13` is recommended in the same commit.
- `globals` 17: split `audioWorklet` environment from `browser`. We use `globals.browser` and `globals.node` — both unaffected.
- `eslint-config-prettier` 10: ESLint 10 compatible; `/flat` entry added in 10.1+ as a separate export (we use the default top-level export which still works).
- RuleTester stricter assertions; not relevant — we have no internal RuleTester usage outside `eslint-plugin-tenant-scope`.

**Code-touch surface area:**
- `eslint.config.js` — keep as-is; current config is already flat-config compatible. Three new recommended rules will need either (a) silencing via override (`"no-unassigned-vars": "off"`) if the codebase has matching patterns, or (b) fixing the offending code. #### Commit 4 — TypeScript 5.6 → 6.0

**Breaking changes (sourced from [TypeScript 6.0 release notes](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-6-0.html) and [Announcing TypeScript 6.0](https://devblogs.microsoft.com/typescript/announcing-typescript-6-0/)):**

TS 6.0 carries the largest set of breaking changes since TS 2.0. The relevant subset for this codebase:

- **`types` compilerOption default changes from "load all from `node_modules/@types`" to `[]`.** This is the most-impactful change for most codebases. **Our `tsconfig.json` already declares `"types": ["node", "vitest/globals"]` explicitly (line 12) — we are pre-immunized.**
- `rootDir` defaults to the directory containing tsconfig.json (was: inferred from input files). Our `tsconfig.json` does NOT set `rootDir` and `include` is `["src/**/*", "tests/**/*", "*.config.ts", "*.config.js"]`. Build output is governed by `tsup` / `vite build` / `svelte-kit sync`, not by `tsc`. **Confirm via local `pnpm build` after bump; expected no-op.**
- `target` default changes from `es5` → `es2023`. We set `"target": "ES2022"` explicitly — pre-immunized.
- `module` default changes from `commonjs` → `esnext`. We set `"module": "ESNext"` explicitly — pre-immunized.
- `strict` default changes from `false` → `true`. We set `"strict": true` explicitly — pre-immunized.
- `noUncheckedSideEffectImports` default changes from `false` → `true`. We don't set this; the default change MAY surface import-only side-effect uses. **Audit `import "./foo"` patterns in `src/` for side-effect-only imports.**

### Pattern 3: Verification Per Commit (load-bearing CI gates per AGENTS.md)

Three gates run on every push to the branch:

### Anti-Patterns to Avoid

- **Mixing two majors in one commit.** Breaks D-04 grouping; if commit 4 (ESLint family) fails CI, you can't tell whether eslint, @eslint/js, eslint-config-prettier, or globals is to blame. The family-grouping rule says "land peer-dep pairs together," NOT "land everything together." Each of the 10 commits is one atomic unit.
- **Force-pushing to fix a red commit.** The branch is `feat/phase-03.0.2-dependency-refresh`; per AGENTS.md Workflow, branches accumulate commits before squash-merge to master. **Use a new commit (`fix(03.0.2): adjust X for Y`) to fix a red intermediate state — do not rewrite history.** The squash-merge at PR time collapses all commits into one master commit, so the per-commit shape is for branch hygiene + bisectability, not master history.
- **Relaxing constraints to make a bump pass.** If TS 6 surfaces 30 new type errors, fix the 30 errors. Do not soften the tsconfig (`"strict": false` or `"noUncheckedIndexedAccess": false`). Do not soften the ESLint config (`"no-restricted-properties": "off"` outside the existing carve-outs). Do not bypass the privacy floor (`REDACT_PATHS` is non-negotiable per AGENTS.md item 6). D-06 says "fix the code"; the constraints are the floor.
- **`pnpm install` without committing `pnpm-lock.yaml`.** CI runs `pnpm install --frozen-lockfile`; a lockfile drift breaks the install step before any test runs. The lockfile diff MUST land in the same commit as the package.json bump.

## Common Pitfalls

### Pitfall 1: Force-relaxing a constraint to make a bump pass
**What goes wrong:** TS 6 surfaces 30 type errors; instead of fixing the errors, the agent sets `"strict": false` or comments out `noUncheckedIndexedAccess`. This violates D-06 ("fix whatever the bumps surface") and AGENTS.md "Security as the floor."
**Why it happens:** Time pressure. Fix-up commit feels endless.
**How to avoid:** D-06 makes it non-negotiable. If a bump's blast radius exceeds the planner's task estimate, the fix-ups still land in this phase. There is no escape hatch.
**Warning signs:** A diff that touches `tsconfig.json`'s `compilerOptions` with relaxations. A diff that adds `// eslint-disable-next-line` directives at scale. A diff that adds `// @ts-ignore` outside narrow third-party-shim sites. A diff that broadens existing carve-outs in `eslint.config.js`.

### Pitfall 2: Missing the dotenv 17 quiet flag → log-pipeline corruption in production
**What goes wrong:** dotenv 17 is bumped without adding `{ quiet: true }`. Boot logs now contain an unstructured `[dotenv@17.x] injecting env (5) from .env – [tip] encrypt with dotenvx: ...` line every time a container boots. promtail/loki ingests this as a non-JSON line and either drops it or escalates a parse error. The structured-log story breaks.
**Why it happens:** dotenv 17's only behavior change is easy to miss in a "trivial bump" mental model.
**How to avoid:** Commit 3's atomic unit MUST include the env.ts edit. Verification: after the bump, run `pnpm test:unit` locally and inspect stdout for the advertising line — its presence is the failure signal.
**Warning signs:** Boot log of a CI run shows a non-JSON line under "Run pnpm test:unit." Smoke job's `docker logs diary-app-1` output contains the advertising line.

### Pitfall 3: pino 10 bump skipping the redact-coverage test as "trivial"
**What goes wrong:** Agent bumps pino + pino-pretty, runs `pnpm test:unit`, sees green, moves on. But the `tests/unit/logger.test.ts` redact-coverage test is the SOLE runtime tripwire for AGENTS.md item 6 — if it had been disabled or skipped, the bump would still appear green while silently weakening the privacy floor.
**Why it happens:** The test runs as one of many under `vitest run tests/unit`; its output doesn't stand out.
**How to avoid:** Explicit check after the bump: `pnpm test:unit -- tests/unit/logger.test.ts` (single-test run) and read the line `redacts every D-24 path with [REDACTED]` is `✓ passed`. CONTEXT.md D-07 designates this as the load-bearing assertion; the planner should put a check-step in the task plan.
**Warning signs:** The test is in `tests/unit/` but `pnpm test:unit` somehow runs zero tests under that path (typically a CI misconfig); a previous PR added `.skip()` to the redact test (search history).

### Pitfall 4: Drizzle pair bump landing 1.0.0-rc into production
**What goes wrong:** The agent reads D-09 ("drizzle is in scope") + D-06 ("no escape hatch") and concludes "land 1.0.0-rc.2." This violates the phase scope statement ("latest **stable**") and the AGENTS.md "Locked stack versions" practice, AND introduces a massive refactor surface (every schema file touches the new casing API).
**Why it happens:** Agent over-interprets "do everything" to include pre-release versions.
**How to avoid:** Path A (recommended in this research) — re-pin at 0.45.2, bump drizzle-kit caret to 0.31.10. Document in PR body: "No major version available on `latest` tag as of 2026-05-11; follow-up phase scheduled when 1.0 stable releases."
**Warning signs:** `package.json` diff contains `"drizzle-orm": "1.0.0-rc.2"`. `drizzle/` directory has new migration files generated by the casing API change. `pnpm db:check` fails with a no-diff violation on master.

### Pitfall 5: ESLint 10 internal plugin breakage (`eslint-plugin-tenant-scope`)
**What goes wrong:** ESLint 10 removes deprecated context APIs (`context.getCwd()`, `context.getFilename()`, `context.getSourceCode()`, `context.parserOptions`, `context.parserPath`). If our internal `eslint-plugin-tenant-scope/index.js` uses any of these, the lint step crashes with `TypeError: context.getFilename is not a function`, and EVERY commit afterward fails CI.
**Why it happens:** The internal plugin is an in-repo `link:` dep, so version-bump tooling doesn't see it. The breakage only surfaces when ESLint 10 runs against it.
**How to avoid:** BEFORE bumping ESLint, audit:
```bash
grep -nE 'context\.(getCwd|getFilename|getPhysicalFilename|getSourceCode|parserOptions|parserPath)\(' eslint-plugin-tenant-scope/index.js
```
If hits: in the same atomic unit, replace `context.getFoo()` with `context.foo` (property accessor).
**Warning signs:** Local `pnpm lint` after the bump produces a stack trace mentioning `eslint-plugin-tenant-scope`. Lint runs in CI take significantly longer / fail with the same trace.
