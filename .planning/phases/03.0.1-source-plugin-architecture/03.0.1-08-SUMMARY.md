key-decisions:
  - "needsReconnect is NOT NULL DEFAULT false (NOT nullable boolean): the tri-state semantic was unnecessary. needsReconnect=true means 'operator must intervene'; needsReconnect=false covers both 'never errored' and 'errored and recovered' (lastErrorAt timestamp distinguishes the two if needed). Saves a defensive null-check at every read site. Migration applies cleanly on shipped v0.1 prod data because the DEFAULT false backfills atomically under the migrate.ts advisory lock."
  - "lastErrorAt uses timestamptz (timestamp with time zone), NOT plain timestamp: the plan's verbatim SQL had `timestamp` (timestamp without time zone). Switched to timestamptz to match every other operational timestamp on data_sources (createdAt / updatedAt / deletedAt are all timestamptz). Mixed timezones on the same row are a future foot-gun. Treated as Rule 1 fix — bug in the verbatim SQL that would have rendered ambiguous timestamps in /sources/[id] banner."
  - "Observability cross-source audit aggregation kept in admin-quota-read.ts (NOT moved into observability.getRecentAudit): the integration test `tests/integration/admin-quota.test.ts` asserts the dashboard surfaces purge.completed / auto_import.deferred / poll.failed — those are cross-cutting verbs not owned by the YouTube adapter. Moving them into the YouTube observability surface would force every future adapter (Reddit etc.) to either no-op or duplicate the cross-source aggregation. Kept the audit query in admin-quota-read.ts; observability.getRecentAudit returns ONLY YouTube-specific verbs (today: quota.service_throttled). Plan's 'kind-decoupled' wording applies to the per-key data shape, which IS routed through observability."
  - "ChargedFetchContext.origin is REQUIRED, not optional: every existing call site (adapter.pollContent / metadata.fetchVideoMetadataByUrl / channel-context-backfill 5 sites) was updated to pass origin explicitly. Defaulting to 'cron' would have hidden user-driven paths (metadata.ts) under the cron pool. Forcing the deliberate decision at every new caller in Phases 6+ is worth the upfront 7-call-site edit."
  - "AdapterError-to-AppError translation in metadata.ts (NOT bubble through to the route): the /api/youtube/fetch-metadata route's existing wire contract is `{ data: ... } | { error: 'upstream_error' | 'not_found' | 'service_unavailable', status: 502 | 404 | 503 }`. Bubbling AdapterError to the route would force the route handler (or a new error mapper) to learn the AdapterError taxonomy. Translating at the metadata.ts boundary keeps the route handler ignorant of the new error type. Same pattern can be applied to other user-facing paths if/when they hit AdapterError-throwing code."
  - "Cron-tier handlers (poll-active / poll-cold / rehab-unavailable) do NOT get try/catch wrappers in this plan: those handlers use pollStatsByVideoId which routes through fetchWithTimeout (NOT chargedFetch) per the deliberate dual-accounting-boundary contract in adapter.ts (writeSnapshot's per-video unitsUsed accounting + SnapshotStatus = 'rate_limited' status path is the chargedFetch alternative). pollStatsByVideoId never throws AdapterError; the wrapper would be dead code. When/if those handlers migrate to chargedFetch (e.g. for fairer reservoir accounting on per-video polling), the same try/catch envelope pattern from poll-user.ts / channel-context-backfill.ts applies."
  - "RateLimiterMemory reset on quota-reset cron tick (NOT just reconcile): RateLimiterMemory's 24h sliding window may not align EXACTLY with the YouTube reset boundary (the reset is at midnight Pacific = 08:00 UTC standard / 07:00 UTC DST; the reservoir's 24h window measures from FIRST consume timestamp). Resetting + reconciling on the cron tick zeroes the reservoir at the exact YouTube boundary, then re-applies today's already-burned units (typically zero on the cron tick because the persistent counter was just trimmed by the same handler — one tick of slight over-allow until the day's first request consumes again). Cleaner than letting the windows drift apart."
  - "Reconciliation attribution: persistent counter sums are attributed to the cron pool ONLY: pre-Plan-08 the persistent counter doesn't carry an origin column, so we can't split today's already-burned units into 'cron used X, user used Y'. Attributing 100% to cron is intentionally conservative — it under-allows user requests until they settle into the user pool's natural cadence. The plan accepts the small over-cautious bias rather than over-allow past the operator's daily envelope. Adding an origin column to youtube_service_quota_usage is a future improvement (would land in a Phase 6 plan if the over-cautious attribution becomes UX-blocking)."
  - "DTO new columns are PROJECTED (not stripped): needsReconnect / lastErrorAt / lastErrorKind are operational metadata for UI banners, not secrets. They are NOT in the AGENTS.md ciphertext-strip list and DO need to cross the wire (the /sources/[id] page reads them to render the 'Reconnect required' banner). Mirrors the metadata column's projection — non-secret, projected explicitly, dto.test.ts pins the field list."
  - "ESLint disable on observability.ts getRecentAudit's audit_log SELECT: cross-tenant aggregation is the intended operator view (D-08). The disable is on the `db` line (where the rule fires), not on the .where line as the plan listing initially placed it. Disable comment carries the same justification as admin-quota-read.ts's audit query (allowlist-gated upstream)."

patterns-established:
  - "AdapterError taxonomy boundary at the HTTP wrapper: cross-source code (channel-context-backfill, poll-user, future Reddit handlers) catch AdapterError once at the handler envelope and route by category. Adapter HTTP wrapper code throws AdapterError; non-adapter code (UI / route handlers) catches AppError. Translation at the boundary (metadata.ts) keeps each layer ignorant of the other's error type."
  - "Reservoir + persistent counter dual-accounting: the in-memory reservoir is fast-path approximation (sub-millisecond consume check); the persistent counter is the authoritative state. Reconcile at boot + at the daily reset cron. Mid-process restart briefly over-allows; that's acceptable because the persistent counter still gates the throttle threshold. Future adapters that need a similar pattern (Reddit's per-app rate limit, Twitter's per-tier cap) follow this template."
