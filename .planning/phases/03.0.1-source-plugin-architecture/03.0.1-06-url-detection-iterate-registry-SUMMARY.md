key-decisions:
  - "Two distinct functions in src/lib/sources/youtube/server/url.ts (parseYoutubeUrl vs youtubeParseUrl) instead of one polymorphic function: parseYoutubeUrl returns a 3-shape discriminated union (channelId / handle / videoId) consumed by the channel-context backfill worker (which needs to know whether a URL is a channel that needs forHandle resolution OR a handle URL OR a video that needs videos.list). youtubeParseUrl returns the generic ParsedUrl shape consumed by the cross-source iterator (which only needs to know whether the URL maps to an event-of-kind=youtube_video, OR not). Collapsing them into one function with a discriminator and a 'this caller doesn't need handles' filter would couple the channel-context worker's view to the iterator's view; keeping them separate lets each consumer ask the question its own way. Same `YT_HOSTS` set is duplicated across both — acceptable cost (5 lines) for the clarity win."
  - "11-char videoId strictness re-enforced at the public services/url-parser.ts boundary (NOT inside youtubeParseUrl): the new youtubeParseUrl is intentionally permissive (any non-empty path segment in /watch /shorts /embed /live /youtu.be is accepted) because future adapter callers (refresh-content endpoint, future Reddit iterator-style pollers) may not care about strict canonical-id shape.
