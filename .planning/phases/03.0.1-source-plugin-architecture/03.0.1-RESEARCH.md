## Summary

Phase 03.0.1 is a structural refactor of code that already works. The architectural decisions D-01..D-17 lock the **shape** (thick adapter, dual-tree per-source layout, props-mapper UI, per-kind queues, 5-category error taxonomy, first-match-wins URL detection, phased migration). Research below focuses on the **execution discipline** that makes that shape survive contact with the codebase: which patterns to copy from established TS plugin ecosystems, which libraries are already in `package.json` and should be reused (instead of hand-rolling), which Phase-03.0 affordances need to be widened or relocated literally vs. re-derived, and which SOTA divergences the planner should accept with eyes open.

Three things in the locked decisions diverge from common practice and the planner should know:

1. **D-09 splits the rate budget at the HTTP layer (~80/20 cron/user)**, but the existing `youtube_service_quota_usage` counter is single-pool per-key per-day. There is no separate `cron pool` / `user pool` row today. The 80/20 split needs a new policy gate inside `chargedFetch` (or a sibling) that consults a pool counter — it is *not* free; the planner must scope a small new mechanism. SOTA equivalent: Stripe SDK / Octokit reserve via separate request queues (Bottleneck reservoirs), not separate counters. Recommendation: **lean on the Bottleneck reservoir pattern using `rate-limiter-flexible` (already in `package.json`)** rather than a new schema column.

2. **D-10's per-kind queue split (`<kind>.poll.cron` / `<kind>.poll.user` / `<kind>.backfill.user`)** diverges from the *current* topology, which uses kind-agnostic names (`poll.active`, `poll.cold`, `poll.user`) plus YouTube-specific extras (`youtube.channel_context_backfill`, `youtube.quota_reset`, `youtube.rehab_unavailable`). The refactor must rename three queues plus retire the kind-agnostic ones. pg-boss queue declarations persist in `pgboss.queue` across deploys — a one-line cleanup in the migration drops the retired rows (precedent: `0010_phase03_baseline.sql` cleaned `poll.hot` / `poll.warm`). This is a **planner-visible task**, not handwave-able.

3. **D-15 first-match-wins URL detection** is the right choice for 5-6 adapters, but the current `services/url-parser.ts` returns a discriminated union with all hosts in one switch — moving that into per-adapter `parseUrl(url) → ParsedUrl | null` introduces a behavioral subtlety: today the parser handles the `reddit_deferred` case explicitly to return a friendly inline-info message (CONTEXT D-18 of Phase 03.0). The new contract returns `null` on no-match → universal route maps `null` to 422 "Not supported by any registered source" — which loses the friendly Reddit deferral message. **Recommendation: keep `parseIngestUrl` as a thin orchestrator** that calls the registry first and only emits the friendly Reddit message if no adapter matched AND host is on a curated "future kinds" list. This is per-the-spirit of D-15 (registry is authoritative) but preserves UX.

**Primary recommendation:** Walk the locked decisions D-01..D-17 verbatim — do not re-debate. Use this research to (a) prescribe libraries already in `package.json` (`rate-limiter-flexible`, native `Error.cause`, `import.meta.glob` for SvelteKit eager imports), (b) flag the three divergences above so the planner scopes them as explicit tasks, and (c) ground the dual-tree refactor in concrete Drizzle / Vite / Svelte 5 mechanics that have changed since the existing `services/integrations/handlers/components` layout was written.

### Locked Decisions

#### Adapter scope (D-01..D-04)

- **D-01:** Adapter scope is **Thick** — each adapter is fully self-contained (HTTP, parsing, persistence, eligibility, cooldowns, observability all live inside `sources/<kind>/`). Cross-source services never switch on `source.kind`.
- **D-02:** Each source plugin uses a **dual-tree layout**: `sources/<kind>/server/` (server-only code, schemas, handlers, http) and `sources/<kind>/ui/` (Svelte components, props mappers).
- **D-03:** UI consistency is achieved via a **standardized props mapper** pattern: each adapter exposes `toCardProps(event) → { thumbnail, title, subtitle, badge, metrics[], href }`. A universal shell component (`src/lib/components/EventCard.svelte`) renders the layout; per-source mappers fill the slots. Same pattern applies to `SourceCardRow`, `SourceDetailHeader`, `DetailMetricsChart`, `QuotaTab`.
- **D-04:** **Escape hatch** for unique layouts: an adapter MAY expose a full Svelte component (e.g. `EventCard.svelte`) that bypasses the standardized shell. Default = mapper. Override = component. Documented but discouraged unless the standard layout cannot accommodate the kind.

#### Credentials and quota (D-05..D-09)

- **D-05:** v0.1 ships **operator-only credentials everywhere**. No per-user OAuth flow exists in 03.0.1.
- **D-06:** **Adapter encapsulates auth/quota mechanics**. Worker handlers, routes, and cross-source services do NOT know envelope-vs-OAuth-vs-scrape.
- **D-07:** **`AdapterContext`** is `{ userId?: string | null; origin: "cron" | "user" }`.
- **D-08:** Each adapter exposes **standardized observability API** (`adapter.observability`).
- **D-09:** **Rate-limit budget reserved for user actions** — ~80/20 cron/user pool split per source.

#### Queue topology (D-10..D-12)

- **D-10:** **Per-kind queues** owned by each plugin.
- **D-11:** Three standard queue suffixes per kind: `<kind>.poll.cron` / `<kind>.poll.user` / `<kind>.backfill.user`, plus kind-specific extras (e.g. `youtube.quota_reset`, `youtube.rehab`).
- **D-12:** **No truly shared async queues** — audit + cross-source DB CRUD are synchronous; only async work is per-kind.

#### Failure model (D-13)

- **D-13:** **Standardized 5-category `AdapterError` taxonomy**: `transient`, `rate-limited`, `not-found`, `permanent`, `operator-issue`. Schema additions: `data_sources.needs_reconnect: boolean`, `data_sources.last_error_at: timestamp | null`, `data_sources.last_error_kind: text | null`.

#### Folder layout (D-14..D-15)

- **D-14:** **Canonical source plugin layout** (see CONTEXT for the full tree).
- **D-15:** **URL detection** — iterate adapter registry, first match wins. Each adapter exposes `parseUrl(url) → { kind, externalId, metadata? } | null`.

#### Migration approach (D-16)

- **D-16:** **Phased migration** — 8-11 incremental commits, each independently CI-green.

#### SOURCE-REFERENCE.md scope (D-17)

- **D-17:** **Sections 1-7, no `_template/` scaffolding files**. Canonical YouTube implementation IS the live reference.

### Pattern 1: DataSourceAdapter widened contract

**What:** Single TS interface that every per-kind adapter implements. Discriminated by `kind`. Carries the existing `pollContent` / `pollStats` / `pollStatsByVideoId` PLUS the new contract surface from D-06..D-08, D-13, D-15.

**Source:** Synthesizes the existing `src/lib/server/integrations/data-source-adapter.ts` with the new D-* obligations. Verified against the actual YouTube adapter shape.

```typescript
// src/lib/sources/adapter.ts (NEW location)
import type { DataSourceRow, EventRow } from "$lib/server/db/schema";

export type SourceKind =
  | "youtube_channel"
  | "reddit_account"     // future
  | "twitter_account"    // future
  | "telegram_channel"   // future
  | "discord_server";    // future

export type EventKind =
  | "youtube_video" | "twitter_post" | "telegram_post" | "discord_drop"
  | "reddit_post" | "conference" | "talk" | "press" | "other" | "post";

export interface AdapterContext {
  /** The user who initiated the work (poll-user, refresh-content). NULL on cron paths. */
  userId: string | null;
  /** Drives rate-limit reservoir split (D-09). "user" = reserved fraction, "cron" = bulk fraction. */
  origin: "cron" | "user";
}

export interface ParsedUrl {
  kind: EventKind;
  externalId: string;
  /** Source-specific extras (e.g., channelId for YouTube). */
  metadata?: Record<string, unknown>;
}

export interface ObservabilityAuth {
  kind: "operator-static-key" | "operator-oauth-app-only" | "scrape" | "operator-oauth-with-user-override";
  /** True when the source REQUIRES per-user OAuth (Phase 6+); false in v0.1 — operator-only. */
  requiresUserSetup: boolean;
  /** True when the operator has configured at least one credential of this kind. */
  isOperatorConfigured: boolean;
```

### Pattern 2: SourceRegistry (runtime Map + assertNever)

**What:** A `Map<SourceKind, DataSourceAdapter>` populated by an explicit barrel. Cross-source code calls `getAdapter(kind)` which throws on unknown kinds via TS's `assertNever` exhaustiveness check.

**Source:** Idiomatic TypeScript — see typescriptlang.org/docs/handbook/2/narrowing.html on exhaustiveness checking with `never`. NextAuth and Strapi use the same pattern (Map of providers populated by explicit imports; runtime throw on unknown).

```typescript
// src/lib/sources/registry.ts
import type { DataSourceAdapter, SourceKind } from "./adapter.js";
import { youtubeChannelAdapter } from "./youtube/server/index.js";

const registry = new Map<SourceKind, DataSourceAdapter>([
  ["youtube_channel", youtubeChannelAdapter],
]);

/** Return value typed as DataSourceAdapter (not narrowed by K — adding conditional
 *  types is an over-engineering trap at 5-6 adapter scale). */
export function getAdapter(kind: SourceKind): DataSourceAdapter {
  const adapter = registry.get(kind);
  if (adapter === undefined) {
    // assertNever-style: when SourceKind union is exhaustively covered above,
    // this branch is unreachable at compile time; if a new kind is added to
    // the union without registry entry, the throw runs and surfaces
    // `unsupported_source_kind` to the route layer.
    throw new Error(`No adapter registered for kind=${kind as string}`);
  }
  return adapter;
}

/** Iterating order is registration order — load-bearing for D-15 first-match-wins. */
export const allAdapters: DataSourceAdapter[] = Array.from(registry.values());
```

**Why not `Map<K, AdapterFor<K>>` with conditional types:** at 5-6 adapter scale the conditional-type plumbing reads like noise. The Map's value type is the union; consumers either know the kind statically (then they cast / branch — usually inside `sources/<kind>/`) or they don't (they call adapter contract methods which are the same across kinds). Done correctly with assertNever the boundary is type-safe.

### Pattern 3: First-match-wins URL routing across registry

**What:** Universal `parseAnyUrl(url)` iterates `allAdapters`, returns first non-null parse result. Replaces the current `services/url-parser.ts` central switch.

```typescript
// src/lib/sources/url.ts (NEW)
import { allAdapters } from "./registry.js";
import type { ParsedUrl, SourceKind } from "./adapter.js";

export type RoutedUrl = ParsedUrl & { kind: SourceKind } | { kind: "unsupported" };

export function parseAnyUrl(input: string): RoutedUrl {
  for (const adapter of allAdapters) {
    const parsed = adapter.parseUrl(input);
    if (parsed !== null) return parsed;
  }
  return { kind: "unsupported" };
}
```

**SOTA divergence callout:** the current `parseIngestUrl` in `services/url-parser.ts` has a special branch that returns `kind: "reddit_deferred"` for Reddit URLs even though no Reddit adapter exists yet. This produces a friendly inline-info message in the UI ("Reddit ingest arrives in Phase 3" — see `services/ingest.ts` line 86). After the refactor, no Reddit adapter → `parseAnyUrl` returns `{ kind: "unsupported" }` → UI shows generic "URL not yet supported".

**Recommendation:** Keep a small "future-kinds host hint" map in `sources/index.ts` for graceful messaging:

```typescript
// src/lib/sources/future-kinds.ts (NEW)
const FUTURE_KIND_HOSTS = new Map<string, EventKind>([
  ["reddit.com", "reddit_post"], ["www.reddit.com", "reddit_post"], ["old.reddit.com", "reddit_post"], ["redd.it", "reddit_post"],
]);

export function detectFutureKind(input: string): EventKind | null {
  try {
    const host = new URL(input.trim()).hostname.toLowerCase();
    return FUTURE_KIND_HOSTS.get(host) ?? null;
  } catch { return null; }
}
```

Then `services/ingest.ts` does:
```typescript
const parsed = parseAnyUrl(input);
if (parsed.kind === "unsupported") {
  const future = detectFutureKind(input);
  if (future === "reddit_post") throw new AppError("Reddit ingest arrives in Phase 3", "reddit_pending_phase3", 422);
  throw new AppError("URL not yet supported", "unsupported_url", 422);
}
```

The `FUTURE_KIND_HOSTS` map is short-lived (will shrink as adapters land) but keeps the UX promise. Planner-visible decision; not strictly load-bearing.

### Pattern 5: Rate budget split (D-09) via rate-limiter-flexible reservoir

**What:** Each adapter HTTP wrapper carries a `RateLimiterPostgres` instance per origin (cron / user). The user-bucket has a smaller reservoir but is always available; the cron-bucket has the larger reservoir and shares the same per-key per-day total.

**Source:** [rate-limiter-flexible Postgres wiki](https://github.com/animir/node-rate-limiter-flexible/wiki/PostgreSQL); the reservoir pattern is also documented in [Bottleneck](https://github.com/SGrondin/bottleneck) and Stripe's SDK retry strategy.

**Important caveat for YouTube specifically:** YouTube's quota model is *daily envelope per key* (10000 units), not per-second / per-minute. The RateLimiter pattern is the right shape but the time window is 24h (Pacific). Use `RateLimiterMemory` for in-process counters, with reconciliation from `youtube_service_quota_usage` on boot. Don't put YouTube quota counts behind `RateLimiterPostgres` — the existing UPSERT-counter pattern in `services/youtube-quota-tracker.ts` is already the canonical store. Add a sibling check before each `chargedFetch`:

```typescript
// sources/youtube/server/http.ts (sketch)
import { RateLimiterMemory } from "rate-limiter-flexible";
import { THROTTLE_NINETYFIVE_THRESHOLD } from "./quota.js"; // 9500

// One reservoir per (date_pacific, origin). Cron gets 80%; user gets 20%.
// Per-day reset via a function call from the youtube.quota_reset cron handler.
const cronReservoir = new RateLimiterMemory({ points: 8000, duration: 86400 });
const userReservoir = new RateLimiterMemory({ points: 2000, duration: 86400 });

export async function chargedFetch(url, picked, units, ctx) {
  const reservoir = ctx.origin === "cron" ? cronReservoir : userReservoir;
  try {
    await reservoir.consume(picked.apiKeyId, units);
  } catch (rejRes) {
    // The bucket is exhausted; throw AdapterError 'rate-limited'.
    throw new AdapterError("rate-limited", "youtube cron pool exhausted; user pool reserved", {
      retryAfterMs: rejRes.msBeforeNext,
    });
  }
  // ... existing fetchWithTimeout + incrementUsage + classify path ...
}
```

**Trade-off the planner must accept:** `RateLimiterMemory` is per-process. Worker has 1 process; that's fine. If 03.0.1 ever introduces multiple worker processes (it doesn't — `APP_ROLE=worker` is one container), switch to `RateLimiterPostgres`. The reservoir reconciliation on boot reads the current `youtube_service_quota_usage` row for today and seeds `points` accordingly.

**Simpler alternative to evaluate:** instead of two reservoirs, gate at the *enqueue* layer in `scheduler/enqueue.ts`: if `getThrottleState() >= "eighty"`, skip cron enqueues but allow `poll-user` and `backfill-user` jobs to proceed. This is the *current* mechanism (Phase 03.0 D-13), and it already preserves user-budget by construction (the user queue's HTTP calls always succeed because cron stops feeding the quota counter at 80%). **The planner should evaluate whether D-09's "explicit reservoir split" is worth the new mechanism vs. the existing throttle-gate at enqueue.** Defensible interpretation: at indie scale, the existing gate IS the 80/20 split — the reservoir is a more elegant restatement. Document the choice; don't ship two parallel mechanisms.

### Pattern 6: Drizzle schema discovery (glob vs barrel)

**What:** Drizzle config's `schema:` field accepts a path or array of paths or a glob. After the refactor, schema files live in two places: `src/lib/server/db/schema/*.ts` (cross-source) and `src/lib/sources/*/server/schema/*.ts` (per-source).

**Source:** [Drizzle config reference](https://orm.drizzle.team/docs/drizzle-config-file); [Drizzle Kit generate docs](https://orm.drizzle.team/docs/drizzle-kit-generate).

**Two viable approaches; pick ONE:**

**Option A — Glob (recommended):**
```typescript
// drizzle.config.ts (UPDATED)
export default defineConfig({
  schema: ["./src/lib/server/db/schema/*.ts", "./src/lib/sources/*/server/schema/*.ts"],
  // ...
});
```
Pro: declarative; new sources auto-discover. Con: `drizzle-kit generate` walks every matched file — schema collision (same table name in two files) silently picks one.

**Option B — Centralized barrel:**
```typescript
// drizzle.config.ts (UPDATED)
export default defineConfig({
  schema: "./src/lib/server/db/schema/index.ts",
  // ...
});
```
Then `src/lib/server/db/schema/index.ts` re-exports per-source schemas via `export * from "$lib/sources/youtube/server/schema/index.js"`. Pro: one file to scan; collision becomes a TS error on the re-export. Con: every new source requires a one-line edit in the central barrel.

**Recommendation: Option A (glob)** — matches D-14 spirit ("add a source = add a folder"). The collision risk is mitigated by the per-source folder convention (`youtube_videos` only ever appears in `sources/youtube/server/schema/videos.ts`). If a future Reddit adapter needs `reddit_videos` (it won't — Reddit is text), the prefix discipline catches it.

**Migration mechanics (load-bearing):** `drizzle-kit generate` produces a diff between the schema (from glob) and migration history. **Moving a schema file from path A to path B with no table name change produces no diff** — Drizzle reads table identity from the `pgTable("name", ...)` first-arg string. The 5 YouTube schema file moves are pure TS source moves; **no migration is required**. Verify with `pnpm db:check` after each move commit (existing CI check).

**Hazard:** the existing `src/lib/server/db/schema/index.ts` barrel re-exports from `./youtube-channels.js` etc. After file moves, those re-exports need updating to `$lib/sources/youtube/server/schema/index.js`. Forgetting this breaks every consumer of `import { youtubeVideos } from "$lib/server/db/schema/index.js"`. The Phase 03.0 grep would surface ~20 such imports — refactor them all in the same commit as the schema move (or the planner accepts a transient broken-build commit, which violates D-16's "each commit independently CI-green" mandate).

### Pattern 7: AdapterError 5-category taxonomy (D-13)

**What:** A single `AdapterError` class with a `category` discriminator. Use Node 22's `Error.cause` for chaining the original error.

**Source:** Node 22 [Error.cause docs](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Error/cause); Honeybadger Node error-handling guide; @satoshibits/functional-errors approach (rejected — too heavy for 5 categories).

```typescript
// src/lib/sources/errors.ts (NEW)
export type AdapterErrorCategory =
  | "transient"        // 5xx, network timeout — pg-boss retry with backoff
  | "rate-limited"     // 429, quotaExceeded 403 — adapter HTTP wrapper waits; cron defers
  | "not-found"        // video deleted, post removed — mark unavailable; tier → Frozen
  | "permanent"        // ToS block, scraping HTML changed — stop polling
  | "operator-issue";  // no keys, key revoked — log + admin banner

export interface AdapterErrorOptions {
  category: AdapterErrorCategory;
  /** Suggested retry delay (ms) when category=rate-limited. */
  retryAfterMs?: number;
  /** Underlying error for log inspection (Node Error.cause). */
  cause?: unknown;
  /** Free-form context for log enrichment. */
  context?: Record<string, unknown>;
}

export class AdapterError extends Error {
  readonly category: AdapterErrorCategory;
  readonly retryAfterMs: number | null;
  readonly context: Record<string, unknown>;
  constructor(message: string, opts: AdapterErrorOptions) {
    super(message, { cause: opts.cause });
    this.category = opts.category;
    this.retryAfterMs = opts.retryAfterMs ?? null;
    this.context = opts.context ?? {};
    this.name = "AdapterError";
  }
}

/** Map an AdapterError to the SnapshotStatus the writeSnapshot service consumes. */
export function categoryToSnapshotStatus(c: AdapterErrorCategory): SnapshotStatus {
  switch (c) {
    case "transient": return "auth_error";   // current behavior — caller logs + retries
    case "rate-limited": return "rate_limited";
    case "not-found": return "not_found";
    case "permanent": return "auth_error";   // current 'auth_error' bucket; planner decides if a 5th SnapshotStatus is needed
    case "operator-issue": return "auth_error";
  }
}
```

**Schema additions (D-13):** `data_sources.needs_reconnect: boolean DEFAULT false`, `data_sources.last_error_at: timestamp NULL`, `data_sources.last_error_kind: text NULL`. Migration is forward-only; new columns are NULL/false-default so existing rows are unaffected.

**Anti-pattern caught:** `throw new Error("rate limited")` in adapter code without `AdapterError` wrapping. The cross-source caller has no way to distinguish retry-able from operator-action-required. ESLint rule (lower priority): `no-bare-throw-error-in-sources` could ban `throw new Error(` inside `src/lib/sources/<kind>/server/`.

**SnapshotStatus mapping (existing):** the current `SnapshotStatus = "ok" | "rate_limited" | "auth_error" | "not_found" | "private"` enum lives in `data-source-adapter.ts`. After the AdapterError taxonomy lands, **keep both**: SnapshotStatus is the adapter→writeSnapshot contract (per-stat result); AdapterError is for control-flow exceptions (whole-batch failures). Don't conflate.

### Pattern 8: Plugin discovery (eager imports via barrel, NOT runtime dynamic-import)

**What:** Each per-source `server/index.ts` and `ui/index.ts` re-exports its public surface. The cross-source `src/lib/sources/index.ts` barrel imports each by static path. The registry constructs from those imports.

**Why NOT `import.meta.glob` for the server side:** the worker process boots from `src/worker/index.ts` which does NOT go through Vite at runtime — it's compiled by `tsup` (see `package.json` scripts: `"build": "... vite build && tsup"`). `import.meta.glob` is a Vite primitive; using it in worker code breaks the tsup build. Use `import.meta.glob` ONLY in the SvelteKit `routes/` tree where Vite is the bundler.

**Why NOT runtime `await import(path)` for plugin discovery:** Vite's production build statically analyzes imports; `await import(variable)` with a non-literal path produces a build warning AND ships the entire `sources/` tree to the client. For the UI side, a Svelte 5 lazy-import pattern is acceptable IF the path is a literal:

```typescript
// src/lib/sources/registry-ui.ts (CLIENT-SIDE)
import type { SourceKind } from "./adapter.js";
import * as youtubeUi from "./youtube/ui/index.js"; // EAGER static import

const uiRegistry = new Map<SourceKind, typeof youtubeUi>([
  ["youtube_channel", youtubeUi],
]);

export function getAdapterUI(kind: SourceKind) {
  const ui = uiRegistry.get(kind);
  if (ui === undefined) throw new Error(`No UI registered for kind=${kind}`);
  return ui;
}
```

For 5-6 adapters, eager imports are fine — Svelte components are tree-shaken at build time and the ui modules are small (props mappers + 5 components).

**SvelteKit-specific gotcha:** pages that consume `getAdapterUI` must import it from `$lib/sources/registry-ui.js` (NOT `$lib/server/...`). The SvelteKit `$lib/server/` barrier rejects client-side imports of server-only files. Per-source `server/` and `ui/` boundary is enforced by SvelteKit's barrier IF (and only if) the per-source `server/` path doesn't contain client-importable code. Convention: every file under `sources/<kind>/server/` is server-only; UI-side never imports from it.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Token bucket / rate-limit reservoir | Custom `class TokenBucket { ... }` | **`rate-limiter-flexible`** (already in package.json — see Standard Stack) | Battle-tested, supports memory/Postgres/Redis backends, handles edge cases (clock drift, refill races) |
| Per-process job-queue retry-with-backoff | Custom `setTimeout(retry)` | **pg-boss `retryDelay` + `retryBackoff: true`** on `boss.send()` options | pg-boss already implements exponential backoff with dead-letter queue routing |
| Cron schedule | Custom interval timer | **pg-boss `boss.schedule(name, cronExpr, payload, { tz })`** | Survives container restart; dedup via internal locking; tz handles DST |
| URL parsing across multi-host | Custom regex registry | **Native `URL` + per-adapter `parseUrl`** | First-match-wins iteration is microseconds for N=6; no library is simpler than `new URL(input).hostname` |
| Error chaining | Custom `wrappedError.original` field | **Node 22 `Error.cause`** | Standard ECMAScript; logger libraries (Pino) understand it natively |
| TypeScript discriminated-union exhaustiveness | Custom runtime kind-switch with default `throw` everywhere | **`assertNever`** in registry's `getAdapter` | Compile-time exhaustiveness via `never`; one runtime throw at the boundary |
| Svelte 5 dynamic component rendering | `<svelte:component>` (deprecated) | **`{@const C = Component}; <C ... />`** | Svelte 5 runes mode native; no compiler warning |
| pg-boss queue declaration drift | Custom `boss.createQueue` per call site | **Existing `QUEUES` registry + `declareAllQueues(boss)` pattern** | Already proven in Phase 1+; centralized queue-name source-of-truth |
| Multi-tenant query scoping | Custom audit | **Existing `eslint-plugin-tenant-scope/no-unfiltered-tenant-query`** | Already deployed, covers AST patterns, has the inline-disable convention |

**Key insight:** Phase 03.0.1 is 90% file moves and 10% new mechanism. The new mechanism (registry, AdapterError, observability surface, refresh-content endpoint, rate-budget reservoir) is small enough to hand-roll inline; the *libraries to add* are zero. Resist the urge to bring in a "plugin framework" lib (Backstage / Nx-style) — at 5-6 adapters those are over-engineering.

## Common Pitfalls

### Pitfall 1: Singleton-key collisions across per-kind queues

**What goes wrong:** When queues are renamed `youtube.poll.cron`, the singleton-key `singletonKey: "active-${minute}-${i}"` from current `enqueue.ts` still works at the queue level (singletonKey is per-queue). But if a future migration tool tries to dual-write to both the old `poll.active` and new `youtube.poll.cron` during a transition window, the same singletonKey across two queues does NOT dedup — both jobs run, double-charging quota.

**Why it happens:** pg-boss singletonKey scope is `(queue_name, singletonKey)`. Different queues with same key are independent.

**How to avoid:** Phased migration D-16 must NEVER dual-write to old + new queue names. The rename commits are atomic within one PR commit: drop old queue subscription + add new queue subscription + cleanup old `pgboss.queue` row in same migration. Pattern from Phase 03.0 baseline: `0010_phase03_baseline.sql` cleaned `poll.hot` / `poll.warm` rows; do the same for `poll.active` → `youtube.poll.cron`.

**Warning signs:** `youtube_service_quota_usage.estimated_units` jumps anomalously after a deploy; `/admin/quota` shows 2× expected unit count for a tier-tick window.

**Citation:** [pg-boss issue #535 — Worker stops working if same singleton key exists in retry & created state](https://github.com/timgit/pg-boss/issues/535) documents that singletonKey is queue-scoped, not global. Don't assume otherwise.

### Pitfall 2: First-match-wins URL parser ordering trap

**What goes wrong:** When Reddit adapter ships in Phase 03.1, its `parseUrl` accepts `reddit.com/r/foo/comments/...`. If the YouTube adapter's `parseUrl` is overly greedy (e.g., regex on the path), it could accidentally match a Reddit-hosted YouTube embed URL.

**Why it happens:** Each adapter's `parseUrl` is written independently; nobody owns the "across-all-adapters URL space". Adding the 6th adapter adds 1 more `parseUrl` to iterate but ALSO requires reviewing the previous 5 for accidental matches.

**How to avoid:** Adapter `parseUrl` first-line MUST be a host check (`if (!YT_HOSTS.has(host)) return null;`) before any path/query parsing. The host check is fast, exclusive, and reads as the adapter's "I claim this domain" signal. Reference: existing `services/url-parser.ts` does this — preserve when moving into `sources/youtube/server/url.ts`.

**Warning signs:** Integration test `tests/integration/url-routing.test.ts` (NEW — the planner should add this) iterates ~20 known URLs and asserts the parsed kind. Adding a new adapter means adding URL fixtures for the new kind; CI catches accidental cross-kind matches.

**Cited from experience (Phase 03.0):** `services/url-parser.ts` already does host-first; mimicking that pattern across per-adapter `parseUrl` preserves the invariant.

### Pitfall 3: Drizzle schema glob ordering & FK collisions

**What goes wrong:** `drizzle-kit generate` walks the glob in OS-dependent order. If `events.ts` (cross-source) references `youtube_videos` (per-source) via FK and the glob discovers per-source files AFTER cross-source ones, the FK validation can produce confusing errors.

**Why it happens:** Drizzle resolves `references()` callbacks lazily (the function is invoked at table construction time, not at file-load time), so file order *should* not matter — but in practice, when you have `pgTable.references(() => youtubeVideos.videoId)`, the `youtubeVideos` import must be reachable in the file-load graph. Re-exports through barrels resolve this; raw glob might not.

**How to avoid:** Keep cross-source schemas in the central `src/lib/server/db/schema/` and per-source in `sources/<kind>/server/schema/`. The barrel `src/lib/server/db/schema/index.ts` re-exports both. Drizzle config's glob covers both directories. Cross-source tables that reference per-source ones (none today, but `events.external_id` is a soft-ref to `youtube_videos.video_id`) use string-name references in JOIN, not FK.

**Verification:** existing `selectEligibleVideoIds` does `JOIN youtubeVideos ON eq(events.externalId, youtubeVideos.videoId)` — no FK is declared between `events.external_id` and `youtube_videos.video_id`. This is by design (per-video refactor 2026-05-06; videos are public-data, events are tenant-owned). Preserve.

**Citation:** [Drizzle config reference](https://orm.drizzle.team/docs/drizzle-config-file) — glob is documented as "single schema.ts file or as many as you want spread across the project".

### Pitfall 4: SvelteKit $lib/server boundary leaking through ui/ imports

**What goes wrong:** A per-source `ui/` component accidentally imports from `sources/<kind>/server/` (e.g., importing a TS type that lives next to the adapter). SvelteKit's barrier is enforced at the `$lib/server/` PATH level — `sources/<kind>/server/` isn't under `$lib/server/`, so the barrier doesn't fire automatically.

**Why it happens:** The per-source dual-tree puts `server/` and `ui/` as siblings. Importing across sibling paths is normal TS; SvelteKit doesn't intervene.

**How to avoid:** Either (a) put a marker comment + lint rule preventing `import` from `../server/` in any `.svelte` or `ui/*.ts` file; (b) name server-only types with a `Server` suffix and re-export only client-safe types via `sources/<kind>/types.ts` (a sibling to server/ and ui/); (c) configure ESLint `no-restricted-imports` for the pattern.

**Recommendation:** Option (b) — small `sources/<kind>/types.ts` re-exports the client-safe types (`SourceKind`, `EventKind`, `CardProps`); UI imports only from there. The server side imports from `types.ts` AND its own server-only types. Convention enforced by code review; planner adds the lint rule if a regression occurs.

**Warning signs:** Vite production build error `[vite] [plugin] cannot bundle server-only module`, or a runtime `ReferenceError` for a Node-only API in the browser.

### Pitfall 5: Per-kind queue rename leaving orphaned pg-boss schedule rows

**What goes wrong:** `boss.schedule(QUEUES.SCHEDULER_TICK_ACTIVE, "0 */6 * * *", {})` writes a row to `pgboss.schedule`. Renaming to `boss.schedule(QUEUES.YOUTUBE_POLL_CRON_TICK, ...)` does NOT delete the old row. Next worker boot has TWO schedules firing — duplicate cron triggers, double quota burn.

**Why it happens:** pg-boss's `schedule` is upsert-by-name; the old name's row is orphaned, not removed.

**How to avoid:** Migration step: `DELETE FROM pgboss.schedule WHERE name IN ('scheduler.tick.active', 'scheduler.tick.cold', 'youtube.quota_reset', 'youtube.rehab_unavailable', 'purge.daily', 'internal.healthcheck');` BEFORE the new schedules are registered. Phase 03.0 did this in `0010_phase03_baseline.sql` for queues; the same SQL needs an explicit DELETE for `pgboss.schedule`.

**Warning signs:** Two `quota.service_throttled` audit rows on the same Pacific day (idempotency normally collapses them — duplicate schedule fires breaks the assumption). Or `youtube_service_quota_usage.estimated_units` doubles for the day.

**Citation:** experience from Phase 03.0 (`0010_phase03_baseline.sql` already cleaned the queue rows; schedule rows were not impacted because all 03.0 schedules were new). 03.0.1 introduces the rename so the cleanup matters now.

### Pitfall 6: `switch (source.kind)` leaking into cross-source code

**What goes wrong:** A cross-source service like `data-sources.ts` or `ingest.ts` writes `if (source.kind === "youtube_channel") { ... } else { ... }`. Adding Reddit adds an `else if`; adding Twitter adds another. The Thick adapter promise of D-01 erodes; per-kind logic accretes in cross-source files.

**Why it happens:** Cross-source code OFTEN has legitimate per-kind needs (e.g., refresh-poll's "is this kind pollable?" check). The temptation is to inline.

**How to avoid:** Add a `canRefreshPoll(event: EventDtoLite): boolean` method to the adapter contract (or a constant `pollableEventKinds: readonly EventKind[]`). Cross-source code calls `getAdapter(source.kind).canRefreshPoll(event)` instead of switching on kind. Same for "is this URL parseable?", "what's the default backfill window?", etc.

**Warning signs:** Grep `switch (source.kind\|switch (event.kind\|case "youtube_channel"\|case "youtube_video"` outside `src/lib/sources/` — every match is a Pitfall-6 instance.

**Recommendation:** Add a custom ESLint rule `no-cross-source-kind-switch` (low priority; planner ships in 03.0.1 if scope permits, defers if not). Until shipped, reviewer checklist for each PR.

### Pitfall 7: Universal shell components rendering before the per-source UI module loads

**What goes wrong:** The /feed page calls `getAdapterUI(event.kind).toCardProps(event)` server-side via `+page.server.ts`. The UI module is imported eagerly in `registry-ui.ts`. But if the registry-ui.ts is imported by both server-side (during data load) AND client-side (during hydration) and the per-source UI module has Svelte component imports, the server-side load can crash with "Cannot use Svelte component in non-Svelte context".

**Why it happens:** SvelteKit pre-renders pages on the server; Svelte components imported in `.ts` modules are NOT runnable on the server outside `+page.svelte` / `+layout.svelte` contexts.

**How to avoid:** Split the per-source `ui/index.ts` into:
- `ui/card-props.ts` — pure functions; importable from server `+page.server.ts`
- `ui/index.ts` — re-exports card-props.ts AND the Svelte components; only importable from `.svelte` files

`registry-ui.ts` exports two registries: `getAdapterUiServer(kind)` returns only `{ toCardProps }`; `getAdapterUiClient(kind)` returns the full surface incl. components. Server-only loaders use `getAdapterUiServer`; `+page.svelte` uses `getAdapterUiClient`.

**Warning signs:** `[vite] error: failed to resolve import "$lib/sources/youtube/ui/EventCard.svelte" from "src/lib/sources/registry-ui.ts"` during `pnpm build`.

**Citation:** experience from Svelte 5 + SvelteKit 2 — the explicit `.svelte` file imports must originate from `.svelte` files. The split-barrel pattern is standard.

### Pitfall 8: `Error.cause` not propagating through pg-boss retries

**What goes wrong:** Worker handler throws `new AdapterError("rate-limited", { cause: originalErr })`. pg-boss serializes the error via `JSON.stringify(err)` → only `{ name, message, stack }` is preserved; `cause` is lost. Retry attempt's log line shows the message but not the chained cause.

**Why it happens:** pg-boss's failed-job archive uses JSON serialization, which doesn't traverse `cause` (it's a non-enumerable property on Error in some Node versions; even when enumerable it's not in JSON.stringify's default visit).

**How to avoid:** Adapter HTTP wrappers MUST log the full error chain via `logger.error({ err, cause: err.cause })` BEFORE re-throwing. The chain is preserved in Pino's structured log but not in pg-boss's failed-job table. Don't rely on pg-boss for diagnostic detail.

**Citation:** [Node Error.cause docs](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Error/cause) — `cause` is a regular property; serialization is library-dependent.

### Pitfall 9: Test mocking strategy drift between Phase 03.0 and 03.0.1

**What goes wrong:** The Phase 03.0 unit tests mock at the module level via `vi.mock("../../lib/server/integrations/youtube-channel-adapter.js", ...)`. After the file moves to `sources/youtube/server/adapter.ts`, ALL existing test mocks break.

**Why it happens:** Vitest's `vi.mock` resolves paths at the module-graph level. Renaming the module path silently breaks mocks that were never updated.

**How to avoid:** Each commit in the phased migration that moves a file MUST update every test that mocks that file in the SAME commit. Grep for the old path in `tests/` BEFORE committing the move. Verify with `pnpm test` (full suite) per commit, not just per file. (The CONTEXT D-16 "each commit independently CI-green" mandate implies this; spell it out for the planner.)

**Warning signs:** Tests pass individually but fail with "module not found" when run as a suite; or worse, tests pass with the OLD mock still in effect (now mocking a non-existent path → real implementation runs in unit test → integration with Postgres / network).

### Pitfall 10: Self-host parity break via APP_ROLE-conditional code in adapters

**What goes wrong:** Adapter code branches on `env.APP_ROLE === "worker"` to enable / disable a feature. The smoke test boots production image with no SaaS-only env vars; the conditional fires unexpectedly and CI green-passes a broken self-host build.

**Why it happens:** Tempting refactor pattern: "the worker doesn't need the UI imports, branch them out to save bundle size".

**How to avoid:** Adapters NEVER read `APP_ROLE`. The split is at the *entrypoint* level (`src/worker/index.ts`, `src/scheduler/index.ts`, SvelteKit) — entrypoints decide what to bootstrap. Adapter code is identical across roles; the bundle split happens via tsup vs Vite config, not via runtime env.

**Recommendation:** Grep for `process.env\|APP_ROLE` outside `src/lib/server/config/env.ts` and `src/<role>/index.ts` — any new occurrence in `sources/` is a P0 review block.

**Citation:** AGENTS.md Self-Host Parity invariant 8.

```typescript
  await boss.work(Q.POLL_USER,      { batchSize: 2 }, async (jobs) => { for (const j of jobs) await handlePollUser(j); });

  await boss.work(Q.CHANNEL_CONTEXT,{ batchSize: 1 }, async (jobs) => { for (const j of jobs) await handleChannelContextBackfill(j); });
}

async function scheduleCronTicks(boss: MinimalBoss): Promise<void> {
  await boss.schedule(Q.POLL_CRON,    "0 */6 * * *", {});
```

### Example 2: AdapterError throw + catch with retry-after honoring

```typescript
// sources/youtube/server/http.ts (RELOCATED + extended)
import { AdapterError } from "$lib/sources/errors.js";

export async function chargedFetch(url: URL, picked: PickedKey, units: number, ctx: AdapterContext): Promise<Response> {
  // ... existing fetchWithTimeout + incrementUsage ...
  if (resp.ok) return resp;

  if (resp.status === 403) {
    const reason = await extractQuotaReason(resp);
    if (reason === "quotaExceeded") {
      throw new AdapterError("YouTube daily quota exceeded", {
        category: "rate-limited",
        retryAfterMs: msUntilMidnightPacific(),
        cause: new Error(`HTTP 403 quotaExceeded on key=${picked.apiKeyId}`),
        context: { apiKeyId: picked.apiKeyId, units },
      });
    }
    // Non-quotaExceeded 403 — credentials revoked.
    throw new AdapterError("YouTube auth failed (operator-issue)", {
      category: "operator-issue",
      cause: new Error(`HTTP 403 ${reason ?? "unknown"} on key=${picked.apiKeyId}`),
    });
  }

  if (resp.status === 404) throw new AdapterError("Video not found", { category: "not-found" });
  if (resp.status >= 500) throw new AdapterError("YouTube transient", { category: "transient" });
  // Unexpected status — surface as transient (operator decides retry policy).
  throw new AdapterError(`Unexpected HTTP ${resp.status}`, { category: "transient" });
}
```

## State of the Art

| Old Approach (likely in Claude's training) | Current Approach (2025-2026) | When Changed | Impact |
|--------------|------------------|--------------|--------|
| `<svelte:component this={X}>` for dynamic rendering | `{@const C = X}; <C ... />` direct usage | Svelte 5 (2024) | Required for runes-mode files; lint warning if you use the old form |
| pg-boss `boss.work(name, { teamSize, teamConcurrency }, handler)` | pg-boss `boss.work(name, { batchSize }, async (jobs) => { for (job of jobs) ... })` | pg-boss v10.0 (2024) | TeamSize / teamConcurrency removed; concurrency now via batchSize + multiple work() calls per queue |
| pg-boss `boss.schedule(queue, cron, payload)` — one cron per queue | pg-boss `boss.schedule(queue, cron, payload, { key })` — multiple keyed cron per queue | pg-boss v11.0 (2025) | Replaces the old "two queues for two cadences" pattern; lets `youtube.poll.cron` carry both Active (`*/6 h`) and Cold (`daily 5am`) schedules differentiated by `key` and payload-tier (see Open Question #2 below) |
| pg-boss `singletonHours: 24` (SendOptions) | pg-boss `singletonSeconds: 86_400` | pg-boss v11.0 (2025) | All time options unified to `*Seconds`; `singletonMinutes` and `singletonHours` removed |
| pg-boss `boss.stop({ wait: true, graceful, timeout })` | pg-boss `boss.stop({ graceful, timeout })` | pg-boss v12.0 (2025) | `wait: true` is always-on now; option removed from `StopOptions` |
| pg-boss `import PgBoss from "pg-boss"` (default export) | pg-boss `import { PgBoss } from "pg-boss"` (named) | pg-boss v12.0 (2025) | Package migrated to ESM + native TypeScript; no default export |
| pg-boss `archiveCompletedAfterSeconds` constructor option + archive tables | pg-boss `deleteAfterSeconds` (default 7d) per-queue or per-job; no archive tables | pg-boss v11.0 (2025) | Completed jobs stay in the job table until `deleteAfterSeconds` elapses; was the most invasive v10→v11 change |
| Plugin discovery via `require.context` (Webpack) | Static barrel imports OR `import.meta.glob` (Vite, server-side restricted) | Vite-first ecosystem (2022+) | Don't use require.context; `import.meta.glob` only safe in Vite-bundled code (SvelteKit routes/), NOT in tsup-bundled worker |
| Custom token-bucket implementation | `rate-limiter-flexible` reservoir or `Bottleneck` reservoir | Standard 2020+ | Hand-rolled buckets miss clock-drift edge cases; libraries handle Postgres / Redis / memory backends |
| Single-table polymorphism with `kind` column + `JSON.parse(metadata)` | Discriminated union in TypeScript over single table | 2020+ | TS 4.0's `as const` + discriminated unions made this idiomatic; covered by Convex, Strapi, NextAuth provider patterns |
| Error subclass hierarchy (`AuthError extends ApiError extends Error`) | Single class with category discriminator + `Error.cause` | Node 16+ for `Error.cause` (mainstream 2022+) | Flatter; works with structured logging; no `instanceof` chain to maintain |

**Deprecated/outdated:**

- **`googleapis` npm package for two-endpoint use** — STACK.md flagged this; Phase 03.0 RESEARCH confirmed via "~3MB transitive deps for 2 endpoints" rationale. Native fetch + zod schemas is the current pattern.
- **`<svelte:component>` syntax** — deprecated in Svelte 5 runes mode. Use direct component reference.
- **pg-boss `teamSize`** — removed in v10. Don't reference in new code.
- **pg-boss `archiveCompletedAfterSeconds`, `retentionDays`/`Hours`/`Minutes`, `singletonHours`, `StopOptions.wait`** — all removed in v11/v12. Use `deleteAfterSeconds` (v12 default 7d), `retentionSeconds` (per-queue), `singletonSeconds`, and `boss.stop({ graceful, timeout })` without `wait` (v12 always waits). The `MinimalBoss` interface in `queues.ts` already insulates most call sites; only `queue-client.ts` and `services/ingest.ts` referenced these.
- **`<svelte:component>`** in runes mode — already noted above; reiterating because per-source `EventCard` override discovery (D-04) will be tempted to use the deprecated form.
- **Per-source quota tables with `user_id`** — public-data semantics (CONTEXT D-07 from Phase 03.0): `youtube_video_snapshots` is shared across tenants, no `user_id` column. Confirm any future per-source schema follows this for public-data tables.

## Open Questions

### 1. Should `tier-resolver.ts` and `poll-eligibility.ts` move into `sources/youtube/server/`?

- **What we know:** Both modules are YouTube-specific in their current implementation (`youtubeVideos` schema reference, `last_poll_status` enum, 24h/28d boundaries). Phase 03.1 will need its own Reddit equivalent (different cadence, different statuses).
- **What's unclear:** Moving them per-source means each adapter's eligibility logic is encapsulated (good for D-01 Thick); leaving them cross-source means one place to look for "what's the polling discipline?" (good for outsider readability).
- **Recommendation:** Leave them in `services/` for 03.0.1 (minimize surface); when Phase 03.1 lands Reddit, move both modules to `sources/youtube/server/` AND create `sources/reddit/server/` siblings as part of THAT phase. Document this future move in SOURCE-REFERENCE.md §6 (Common Patterns).

### 2. Should the cron tier-tick scheduler split (POLL_ACTIVE vs POLL_COLD) collapse into one queue with payload `{ tier: "active" | "cold" }`?

- **What we know:** D-11 mandates `<kind>.poll.cron` (single suffix). Current 03.0 has `poll.active` + `poll.cold` (two queues). pg-boss is now on v12.18.2 (bumped 2026-05-08) — v11+ added `key`-based multiple schedules per queue, which is the canonical primitive for this collapse.
- **The v11+ pattern (now available):**
  ```ts
  // src/scheduler/index.ts
  await boss.schedule(QUEUES.YOUTUBE_POLL_CRON, "0 */6 * * *", { tier: "active" }, { key: "active" });
  await boss.schedule(QUEUES.YOUTUBE_POLL_CRON, "0 5 * * *",   { tier: "cold"   }, { key: "cold"   });
  ```
  Two schedules, same queue, distinct `key` rows in `pgboss.schedule`. Worker subscribes once to `youtube.poll.cron`, handler reads `job.data.tier` and dispatches.
- **Why `key` matters (vs the v10 "two anonymous schedules" hack):** v11+ exposes `unschedule(queue, key)` and `getSchedules(queue, key?)` — schedule rows are addressable individually. Migration path between cadence policies (e.g. add a `frozen` tier, swap Active cron) is `unschedule(queue, oldKey)` + `schedule(queue, newCron, payload, { key: newKey })`. On v10 you had to drop the entire queue's schedule list to change one cadence.
- **Recommendation:** Collapse to `youtube.poll.cron` with two `boss.schedule(..., { key })` calls. Handler is one `boss.work(QUEUES.YOUTUBE_POLL_CRON, async (jobs) => { for (job of jobs) dispatchByTier(job.data.tier, job.data) })`. Migration `0020_pg_boss_v12.sql` already drops the v10 `pgboss` schema, so the old `poll.active` / `poll.cold` schedule rows die naturally — no manual cleanup needed. `singletonKey` per-job is queue-scoped (Pitfall 4 still applies), so per-event dedup keys must include the tier prefix if both tiers can hit the same event.
- **Source:** [pg-boss v11.0.0 release notes](https://github.com/timgit/pg-boss/releases/tag/11.0.0) — "Queues now support multiple schedules. Previously, you could only set one cron expression, but a new option was added, `key`, that supports a schedule per unique key."

### 3. Where does the Universal `EventCard` shell live — `src/lib/components/` or `src/lib/sources/components/`?

- **What we know:** CONTEXT marks this as Claude's discretion. The shell is universal (no per-source code); convention says cross-cutting universal components live in `src/lib/components/`.
- **Recommendation:** `src/lib/components/EventCard.svelte` — preserves the existing convention; `src/lib/sources/components/` would be a new dir holding ONE component (cluttered). The per-source overrides (when they exist) live in `sources/<kind>/ui/EventCard.svelte`. Naming clash is fine — Svelte resolves by import path.

### 4. Does the rate-budget split (D-09) need a new schema column, or can it ride on `youtube_service_quota_usage`?

- **What we know:** Current schema is `youtube_service_quota_usage(date_pacific, api_key_id, estimated_units)` — single counter per (key, day). No origin discrimination.
- **What's unclear:** Does D-09's "user pool reserved" need its own counter, or can it live in-memory in the adapter HTTP wrapper? Per Pattern 5 above, the recommendation is in-memory `RateLimiterMemory` reservoir reconciled to `youtube_service_quota_usage` on boot — NO new column.
- **Recommendation:** No schema change. Add `originPool: "cron" | "user"` as a parameter to `chargedFetch` and consult two in-process reservoirs. Reconciliation on worker boot reads today's `estimated_units` and seeds both reservoirs proportionally. Document the lossy aspect (process restart resets the per-pool split, but the daily counter is preserved). Acceptable trade-off at indie scale.
