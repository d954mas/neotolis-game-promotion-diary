key-decisions:
  - "Registry boundary cast `youtubeUiServer as unknown as AdapterUiServer`: the per-kind module's toCardProps signature is `(event: YoutubeEventLite) → CardProps`; the registry's contract requires `(event: unknown) → CardProps`. TypeScript sees this as contravariant and refuses the assignment. Solution mirrors the server-side registry.ts pattern: cast at the registration point, document the narrowing happens INSIDE the per-kind mapper (today YoutubeEventLite is a structural subtype of EventDtoLite — every field used by toCardProps is present on the /feed loader's row shape). No runtime cost. Alternative (changing the per-kind signature to `(event: unknown)` + casting INSIDE) would push unsafe casts into every per-source mapper — rejected as worse."
  - "EventCard.svelte minimal styling (NOT preserving FeedCard.svelte's Phase 02.1-23 redesign features): the plan's <interfaces> section explicitly notes CardProps is minimal — kind icon + Inbox badge + Mine treatment + clipped notes + associated-games block are NOT yet exposed. Two options were available: (a) extend CardProps to cover all the redesign features now, OR (b) keep CardProps minimal and let Phase 03.1 extend it when the second kind lands. Picked (b) per CONTEXT.md philosophy 'three concrete callers earn an abstraction; one or two does not'. With only YouTube renderable, extending CardProps would freeze guesses about what Reddit / Twitter need. Plan accepts the universal shell renders a STRIPPED version of the FeedCard visual — but the stripped shell is NOT shipped to production routes (FeedCard stays). When Phase 03.1 lands Reddit and the /feed migration is real, CardProps will extend with the load-bearing fields (kindIcon, isInbox, isMine, notes, attachedGames[]) — the contract grows from real concrete needs."
  - "FeedCard.svelte UNCHANGED: the plan's <interfaces> section spelled out the scope decision — ship the mapper + registry + universal shell as a TESTED contract, but DO NOT migrate /feed away from FeedCard.svelte in this plan. Reasoning: behavioral identity is the load-bearing CI gate (existing /feed browser tests, /sources interactions, /games detail rendering). Migrating /feed to use EventCard with a stripped CardProps would regress UX on a production surface for zero user benefit (only one kind exists; the dispatch demonstrates nothing). When Reddit lands in Phase 03.1, EventCard's CardProps grows + /feed migrates — same plan, real consumer."
  - "eventKindToSourceKind co-located in src/lib/sources/ (NOT in src/lib/server/services/events.ts): the helper is a pure compile-time mapping from the EventKind union to the SourceKind union. It's NOT cross-tenant data. NOT a service call. Putting it next to the adapter / registry / card-props files keeps the cross-source dispatch surface in one place. Imported by future EventCard consumers (currently only the unit test for the bridge); /feed continues to use FeedCard which has its own switch statement on event.kind for image-source rules — that switch will collapse into eventKindToSourceKind when the migration happens."
