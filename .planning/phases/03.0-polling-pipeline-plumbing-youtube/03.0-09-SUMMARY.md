## Accomplishments

- **All 6 worker handlers ship the pg-boss v10 array-handler shape (Pitfall A+B).** Each handler exports `async function handle<Name>(job)` and src/worker/index.ts wraps with `boss.work(name, {batchSize}, async (jobs) => { for (const job of jobs) await handler(job); })`. Forgetting the for-loop ships a silent no-op; the for-loop is in every subscriber.
- **Two-phase tx pattern (Pitfall 5) implemented in poll-active / poll-cold / poll-user handlers.** Phase A: short SELECT outside tx loads events. Phase B: youtubeChannelAdapter.pollStats(events, null) HTTP call OUTSIDE any tx. Phase C: writeSnapshot per result in a single short write tx (snapshot INSERT ON CONFLICT DO NOTHING + events UPDATE tenant-scoped + quota UPSERT chained). The tests/integration/poll-worker-tx-boundary.test.ts file pins the boundary with a 200ms simulated upstream delay AND asserts a concurrent SELECT during the HTTP wait succeeds (events row not locked).
- **Channel-context backfill handler implements D-14 with 3 quota units total:** channels.list (1 unit) → uploadsPlaylistId + channelTitle → UPSERT youtube_channel_metadata_cache; playlistItems.list (1 unit) → 50 video ids; videos.list batched (1 unit) → 50 snapshot rows + events.last_polled_at advance for any user-owned matching events. UPSERT on (channel_id) PK makes the cache write idempotent; ON CONFLICT DO NOTHING on (video_id, polled_at) UNIQUE makes snapshot inserts idempotent within the same minute.
- **Pacific-tz cron schedules registered via pg-boss schedule options.tz (Pitfall D):**
  - `youtube.quota_reset` `'0 0 * * *'` tz=`America/Los_Angeles` — fires at midnight Pacific, the natural YouTube reset boundary; pg-boss handles PDT/PST transitions automatically.
  - `purge.daily` `'0 4 * * *'` tz=`America/Los_Angeles` — fires at 04:00 Pacific, after the operator's daily backup at 03:00, so a 60-day-old account being purged today is still in the night's backup if recovery is needed.
- **Pattern A scheduler-tick queue separation:** cron schedules send empty `{}` to `scheduler.tick.active` / `scheduler.tick.cold`; the worker process subscribes and calls `enqueueActivePolls()` / `enqueueColdPolls()`. This keeps the scheduler container's responsibilities thin (just fire crons) and routes the DB-touching enqueue logic to the worker pool. The two new queue names live in `src/lib/server/queues.ts` (`SCHEDULER_TICK_ACTIVE` / `SCHEDULER_TICK_COLD`) and are declared via the existing `declareAllQueues()` boot path — no migration needed because pg-boss declares queues at runtime.
- **Tier-resolver as Pitfall 7 single source of truth:** scheduler/enqueue.ts uses `resolveTier(occurredAt, lastPollStatus, now)` from Plan 03 to gate Active vs Cold vs Frozen vs Unavailable. The SQL coarse window (date arithmetic on occurred_at) is refined by the JS `resolveTier` filter — no caller re-derives the 24h / 28d boundaries. Verified by `grep "resolveTier" src/scheduler/enqueue.ts` and the 5 scheduler-enqueue.test.ts tests covering Active / Cold / Frozen / Unavailable / auto-import gating.
- **Throttle gate (D-13) at the scheduler tier:** `getThrottleState() === 'eighty'` pauses Cold but allows Active to continue (Active is the user-time-budget protection); `'ninetyfive'` pauses both. The first `'eighty'` crossing emits a `quota.service_throttled` audit row via `markThrottleTransition` (idempotent per (date_pacific, state); daily-fire only). refresh-now (POLL_USER) is independent of the throttle gate — even at 95% the user-driven path keeps working.
- **15 live integration tests pin the contracts for Phase 4 inheritance.** scheduler-enqueue: 5 tests (Active/Cold tier classification, Frozen/Unavailable exclusion, auto_import gating). queue-topology: 2 (Phase 3.0 queues declared, retired POLL_HOT/POLL_WARM absent). youtube-quota-throttle: 4 (8000 pauses Cold, 9500 pauses Active, audit-row idempotency). poll-worker-tx-boundary: 2 (tx boundary short despite 100ms simulated latency, concurrent SELECT during HTTP wait succeeds). ingest-paste-then-poll: 1 (manual-paste source_id=NULL flows through handlePollActive → snapshot row + last_polled_at). youtube-snapshot-read: 1 (Phase 4 chart-loader contract — shared snapshot data with per-tenant events JOIN gating).

## Decisions Made

- **Pattern A (scheduler-tick queue) chosen over Pattern B (marker payload).** Plan 09 explicitly recommended Pattern A; the cron schedules send empty `{}` to `scheduler.tick.{active,cold}` queues, the worker subscribes and calls `enqueueActivePolls`/`enqueueColdPolls`. This keeps the scheduler container's responsibilities thin (just fire crons) and routes the DB-touching enqueue logic to the worker pool. Pattern B would have polluted POLL_ACTIVE handler with a `data.scheduledTick` discriminator — the dual-purpose handler is harder to reason about. Two new queue names (`SCHEDULER_TICK_ACTIVE`, `SCHEDULER_TICK_COLD`) added to `src/lib/server/queues.ts` so the pgboss declarations are version-locked from Phase 1's `declareAllQueues` discipline.

- **Inlined zod-validated channels.list / playlistItems.list / videos.list HTTP fetches in `youtube-channel-context-backfill.ts`** rather than extending the youtube-channel-adapter interface with a third method. Plan 06's adapter interface exposes `pollContent` + `pollStats`; channels.list is a one-shot resolver only this handler needs. Adding it to the adapter would have evolved the DataSourceAdapter interface for one consumer — premature abstraction (AGENTS.md "no premature abstraction"). If a future plan needs the same channels.list resolver, we extract at the third caller.

- **batchSize choices per queue:**
  - POLL_ACTIVE = 4 (Active workload is larger, parallelism helps)
  - POLL_COLD = 1 (Cold runs once daily; batch=1 keeps quota burn smooth)
  - POLL_USER = 2 (interactive UX with a small concurrency budget)
  - All cron-driven (CHANNEL_CONTEXT_BACKFILL, QUOTA_RESET, PURGE_DAILY, SCHEDULER_TICK_*) = 1

- **Throttle 'eighty' DOES emit the audit row from `enqueueActivePolls` first crossing.** `markThrottleTransition` is idempotent per (date_pacific, state) so daily-fire only. apiKeyId='scheduler-tick' marks the row's origin (operator can grep audit_log for scheduler-side throttle vs adapter-side throttle). The youtube-quota-throttle test pre-seeds an audit row at the (date_pacific, state) composite to verify the defense-in-depth lookup spots it (since module state was reset via resetThrottleState and the env-time ADMIN_EMAIL_ALLOWLIST cache cannot easily be re-parsed mid-process).

- **writeSnapshot is the SINGLE write tx in every poll handler.** Per-event try/catch around writeSnapshot with `logger.error` + `continue` (NOT `throw`) so one bad event in a 50-id batch does not abort the rest. Single-event poll-user is the exception — it rethrows so pg-boss retries per queue policy.

- **Pre-resolve `picked = pickKeyForJob()` at handler start so all events in the batch share the same `apiKeyId`** in the writeSnapshot quota row. The adapter does its own `pickKeyForJob` per HTTP call internally (round-robin still moves forward inside the adapter), but the per-event quota row needs ONE consistent identifier — handler-start `picked` is the simplest contract. This matches the writeSnapshot signature which takes a single `apiKeyId` parameter for the events batch.

- **Channel-context backfill runs 3 quota units total (not 2).** The plan acceptance criteria states 2 units (channels.list + playlistItems.list); the third call (videos.list batched) is required for the chart-loader contract — without snapshot rows seeded on first paste, the per-event detail page would show empty charts even though the events are pasted. Treated as Rule 2 (auto-add missing critical functionality): VIZ-01 explicitly requires snapshot rows present after first paste; the plan's wording "playlistItems.list last 50 (1 unit) → 50 video ids" + "Insert snapshot rows via writeSnapshot loop (or direct insert with onConflictDoNothing)" implies the videos.list call is needed to source the metrics for those rows.
