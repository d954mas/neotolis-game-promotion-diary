# Phase 03.0 Plan 10: Channel-Context Backfill Trigger Summary

**When the user pastes a YouTube URL whose channel is not yet in `youtube_channel_metadata_cache`, ingest enqueues ONE `YOUTUBE_CHANNEL_CONTEXT_BACKFILL` job (idempotent via pg-boss singletonKey = channelId + singletonHours: 24); subsequent pastes from the same channel hit the cache and skip the enqueue.**

## Decisions Made

(See frontmatter `key-decisions` block for the canonical list — repeated here narratively.)

- **Read-back-from-row vs duplicate oEmbed call.** `enrichFromUrl` (in events.ts) already populates `events.metadata.author_url` from the oEmbed response BEFORE returning. The trigger reads back from the just-created event row's metadata field rather than calling oEmbed again. Saves one HTTP roundtrip on every successful YouTube paste — non-trivial because YouTube's oEmbed is slower than 100ms p99 and the paste flow is a hot user-facing path.
- **Per-shape singletonKey strategy.** `/channel/UC…` URLs → extract UC id and use as singletonKey + cache lookup key (canonical 24-char id). `/@handle` and `/c/customname` URLs → use the FULL URL as the singletonKey + cache lookup key (the backfill handler resolves the UC id at handler-time via `channels.list?forHandle=`). The trade-off: a `@handle` paste followed later by a `/channel/UC…` paste of the same channel will miss the cache twice (first paste resolves and writes cache keyed on UC id; second paste's lookup key is the UC id, which now hits — actually fine). The bad path is two `@handle` pastes for the same handle 25h apart: the second misses the cache (lookup key = handle URL, but cache row exists keyed on UC id) AND the singletonHours: 24 window has expired, so a second backfill fires (2 quota units burned). Acceptable for MVP; documented as a follow-up if quota becomes scarce.
- **Fire-and-forget error swallowing.** The backfill is a Phase 4 chart enhancement (CONTEXT D-14: median-context for the user's "compare with other videos on the channel" use case), NOT load-bearing for the paste flow. The user pastes a URL → expects 201 with the event row → backfill happens "in the background" and improves the experience eventually. A pg-boss schema-not-yet-created error (test that forgot to mock), a DB hiccup on the cache lookup, or a transient pool exhaustion must not surface as a 502 on the user-facing POST `/api/events`. The try/catch wraps the entire enqueue path; on error we log at WARN with the authorUrl context and return — the paste still returns 201.
- **No audit row.** The plan's `must_haves` block does NOT require an audit row, and the `audit_action` enum is locked by Plan 01's migration 0010 (no `ingest.channel_backfill_requested` verb shipped). Adding a new enum verb requires a forward-only migration which is out of scope for this plan. The backfill HANDLER (plan 09) writes `auto_import.deferred` on cache-hit / quota-throttle outcomes, which IS the user-visible audit signal; the trigger fire is a pure side-effect of paste and writes no audit row of its own.

## Follow-up Items

1. **Audit verb for the trigger fire (optional, low-priority).** If the operator wants observability into "how many channels have been backfilled this week", a future migration could add `ingest.channel_backfill_requested` to the `audit_action` enum. Out of scope for plan 10 — the boss.send itself is the observability signal (queue depth on `youtube.channel_context_backfill`).

2. **Quota math under the @handle path.** The current per-shape singletonKey strategy has a known edge case: two `@handle` pastes 25h apart for the same channel will burn 2 quota units (singletonHours expired + cache lookup keyed on URL, but cache row keyed on UC id). For the operator's expected paste rate this is negligible; if the operator's quota becomes scarce, the fix is either (a) extend `singletonHours` to 168 (one week), or (b) teach the trigger to do a `channels.list?forHandle=` itself to resolve the UC id before the cache lookup (cost: 1 extra Data API unit per paste). Track in deferred-items if Phase 4 surfaces quota pressure.
