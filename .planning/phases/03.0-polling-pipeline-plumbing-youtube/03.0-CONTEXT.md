Reddit's per-user OAuth model and Steam's per-publisher model are different enough from YouTube's service-level model that bundling would force premature abstraction. ROADMAP updated to reflect the split (Wave 0 task in 03.0-PLAN.md commits the rename + REQ-ID redistribution before any code change).

- **D-02 — YouTube spike (`videos.list` batched quota math) runs as Wave 0 Task #1 of 03.0-PLAN.md.** Live HTTP call against operator's API key with `quotaUser` parameter; expected response shape: 50 videos for 1 unit. Result logged in 03.0-RESEARCH.md as verified fact. If actual cost differs (e.g. Google moved to 5 unit per batched call), worker design re-pivots before any worker code lands. Reddit `/about/rules.json` spike — Phase 3.1 only.

- **D-03 — ROADMAP rename happens **before** plan-phase, not as part of execution.** The user explicitly requested this so /gsd:plan-phase reads the post-split scope. ROADMAP edits committed alongside this CONTEXT.md. Future /gsd:plan-phase invocation references Phase 3.0 (not the original Phase 3).

- **D-04 — Wave breakdown: 5 waves with manual UAT checkpoints (Phase 2.1 style).** Wave 0=spike+migration+scaffolding; Wave 1=services; Wave 2=routes+admin middleware; Wave 3=workers+scheduler cron+adapter; Wave 4=UI polish (PollingBadge live + /admin/quota page + Permanent-delete-now CTA); Wave 5=smoke+verify. **Manual UAT mandatory after Wave 3 and Wave 4.** Target ~12–15 atomic plans (gap closure adds in round-N pattern per Phase 2.1 precedent if UAT surfaces issues). The 5-wave structure is the load-bearing review surface — three-wave compression rejected because UAT after Wave 3 catches "polling broke /feed badge" / "auto-import wrote duplicates" before Wave 4 polish builds on top.

### Polling Tiers (POLL-01..05)

- **D-05 — Three tiers + Frozen border (revised twice during discussion):** `Active 0–24h` (4×/день, every 6h) · `Cold 1–28д` (1×/day) · `Frozen >28д` (polling stops; refresh-now only). The original ROADMAP "Hot/Warm/Cold + Stale" model is RETIRED. Boundaries computed from `events.occurred_at`, not `events.created_at` (the user-meaningful timestamp; user explicitly clarified during discussion). Frozen tier eliminates Pitfall 17 (Postgres bloat) by construction — each video accumulates ~31 snapshots over 28 days then stops growing; ~1.5MB/year storage even at 1000 videos/year (D-NEW retention math).

- **D-NEW (retention) — Keep all `youtube_video_snapshots` raw forever; no rollup needed in 3.0 or Phase 6.** Frozen tier IS the retention mechanism — snapshot stream is asymptotically bounded per video (Hot 4 + Cold 27 + occasional refresh-now). Reality check: 1000 active videos × 31 snapshots = 31k rows = ~1.5MB. Schema partition-friendly (`id uuidv7 PK + (video_id, polled_at, metric_key) UNIQUE`); rollup only if Phase 6+ trigger fires (`table > 500MB OR p95 chart query > 200ms`). AGENTS.md "no premature abstraction" — defer.

- **D-NEW (idempotency) — `polled_at` truncated to minute** in `youtube_video_snapshots` UNIQUE constraint. Worker writes `polled_at = date_trunc('minute', now())`; INSERT ON CONFLICT DO NOTHING idempotent across worker retries within the same minute. Active tier's 6h cadence has 360× resolution buffer. Refresh-now's 5min cooldown prevents user-driven duplicate concerns.

- **D-NEW (PollingBadge copy) — Terse English style:** `Hot · checked Xh ago` / `Cold · yesterday` / `Frozen · refresh to update` / `Unavailable · last seen Xd ago`. 5 Paraglide keys; concrete copy lands in UI-SPEC if /gsd:ui-phase 3.0 fires, otherwise planner Discretion. UI English-only per UX-04; Russian locale translates later. (Note: "Hot" terminology kept in user-facing copy for brevity even though tier renamed Active internally — refers to the Hot 0–24h period; users won't confuse with the dropped legacy "Hot/Warm/Cold/Stale" 4-tier system.)

### YouTube Adapter Scope (POLL-01..06, INGEST-02..04)

- **D-06 — Service-level YouTube quota model (DEVIATION from PROJECT.md "Per-user API keys" — for YouTube only).** One env var `SERVICE_YOUTUBE_API_KEYS` (comma-separated, 1+ keys; operator's keys in prod, self-host operator's keys in self-host). Worker round-robins across keys; per-key quota state tracked in `youtube_service_quota_usage`. Shared snapshot cache by `video_id` — 50 users tracking @sebastianlague = 1 poll feeds all of them. PROJECT.md "Key Decisions" amended to split per-platform: YouTube service-level, Reddit + Steam stay per-user (Pitfall 11 for Reddit; per-publisher data for Steam).

- **D-07 — Snapshot cache shape: global `youtube_video_snapshots` table, no `user_id` column.** Public-data semantics — same view count is the same view count regardless of which user's event references it. ESLint TENANT_TABLES allowlist extends with explicit comment `// public external data, no tenant scope`. Phase 4 chart loader: `SELECT FROM youtube_video_snapshots WHERE video_id = e.external_id JOIN events e WHERE e.user_id = $userId`. AGENTS.md Privacy invariant 1 (tenant scoping) preserved at the `events` table level — each user only sees events they own; the snapshot data is just the public stats counter. The non-tenant-scoped allowlist gets explicit narrative justification in the ESLint plugin file header.

- **D-08 — Per-user YouTube key override DEFERRED to Phase 6.** Phase 3.0 ships service-level only. Trigger to revisit: `>=1 power user trips 95% of operator's quota`. Until trigger, KEYS-01 from REQUIREMENTS.md is rephrased as "Phase 6 polish — per-user override for high-volume users; Phase 3.0 ships service-level only." No `/keys/youtube` UI in 3.0. No `api_keys_youtube` table in 3.0.

- **D-09 — Channel-registration backfill picker (5 presets, default 30):** When user registers a `youtube_channel` via `/sources/new`, second-step UI offers `1 / 7 / 30 / 90 days / Everything` with `30` as default. The `1d` preset gives "only new content from this moment" semantics. Backfill cost: 1 unit per playlistItems.list page (50 videos/page). 30d preset for active devlog ≈ 1 unit; Everything for 1000-video channel ≈ 20 unit one-time.

- **D-10 — Refresh-now: icon `[🔄]` on `<PollingBadge>` for any pollable event with `last_polled_at IS NOT NULL` OR Frozen.** Click → POST `/api/events/:id/refresh-poll` → enqueues to `poll.user` queue. Rate limit: **1 click per event per 5 minutes**, persisted in `events.metadata.last_user_refresh_at`. Within window: service throws AppError 429 `too_many_refreshes` with retry-after metadata; UI disables button + tooltip "Wait Xm". Visual: spinner ~5s → polled-just-now state. Available even for Frozen events (this is the only way to update them).

- **D-11 — Manual paste does NOT auto-create a `data_source` row.** Stats polling in service-level model works on `events.external_id` (video_id) directly — `data_source` row not needed. Phase 2.1 D-05 `findSourceByAuthorUrl` continues to inherit `author_is_me=true` if oEmbed `author_url` matches an existing owned-by-me data_source. If user later wants auto-import from this channel — they explicitly add via `/sources/new`. Eliminates "junk" data_source rows from one-off blogger video pastes.

- **D-12 — `not_found` / `private` / `auth_error` from `videos.list`: mark event off polling.** Worker writes `events.last_poll_status` to the appropriate code + stops scheduling (effectively Frozen-without-the-28d-wait). PollingBadge renders `Unavailable · last seen Xd ago`. Refresh-now stays available (video might un-private later). Audit `event.poll_failed` once on first failure (not every retry). Snapshot history is preserved — Phase 4 chart can render "video lived until date X".

- **D-13 — Service quota tracking: `youtube_service_quota_usage(date_pacific, api_key_id, estimated_units)` table.** Worker increments after each call (in same tx as snapshot insert). Scheduler reads at enqueue time; if today's usage on any key ≥80% → pauses Cold + auto-import (Active + refresh-now continue). At 95% → pauses Active too. Reset cron `0 0 * * *` (midnight Pacific). Audit `quota.service_throttled` once per threshold crossing per day. NO Google-API quota header (YouTube doesn't return remaining-quota in responses); we estimate ourselves, refresh from manual Cloud Console UI is operator's job for ground truth.

- **D-14 — Channel context backfill (one-time per channel):** When user pastes a video from a channel not in `youtube_channel_metadata_cache(channel_id, …)` (global cache, no user_id), worker enqueues a one-shot job: `playlistItems.list` last 50 videos (1 unit) + batched `videos.list` snapshot all 50 (1 unit) = 2 unit. Caches channel meta + populates 50 video rows in `youtube_video_snapshots`. Subsequent paste from same channel = cache hit, zero extra quota. Phase 4 chart median ("trailer = 15k views; channel median = 5k → outperformed 3×") uses these snapshots.

- **D-15 — Manual-paste dedup: partial unique index `events_user_kind_ext_active_unq ON events(user_id, kind, external_id) WHERE external_id IS NOT NULL AND deleted_at IS NULL`.** Closes a Phase 2.1 schema gap — existing `events_user_kind_source_ext_unq` covers only `source_id IS NOT NULL` (auto-import dedup); manual paste of the same `youtube.com/watch?v=abc123` twice currently inserts two rows. Phase 3.0 baseline migration adds the second partial index. Service throws AppError 422 `duplicate_event`.

- **D-16 — Admin panel `/admin/*` gated on `c.var.userEmail in env.ADMIN_EMAIL_ALLOWLIST` (comma-separated emails, empty default = `""`).** Empty allowlist → all `/admin/*` returns 404 (anonymous-401-sweep style). CI smoke gate boots image with empty allowlist → asserts /admin/quota returns 404 (self-host parity preserved by construction). **AGENTS.md "no hard-coded admin allowlist" check passed** — env-configurable, not hard-coded; same semantics as `SUPPORT_EMAIL` (Phase 02.2 D-32). Phase 3.0 ships exactly one page: `/admin/quota` with today's `youtube_service_quota_usage` per key + last 50 service-level audit entries (`quota.service_throttled` / `purge.completed`). Phase 6 expands `/admin/*` shell with per-user QUOTA-01 dashboards for all users. `.env.example` documents `ADMIN_EMAIL_ALLOWLIST=you@example.com,colleague@example.com` (default empty).

- **D-NEW (Shorts handling) — YouTube Shorts handled identically to regular videos.** Same `videos.list` and `playlistItems.list` endpoints; same quota cost. Worker stores `events.metadata.duration_seconds` and derived `events.metadata.is_short` (true if duration ≤ 60s) at snapshot time — useful for Phase 4 UX (filter shorts vs regular) but no user-facing feature in 3.0. No extra schema work (events.metadata is jsonb).

- **D-NEW (Throttle visibility) — Service quota state visible ONLY in `/admin/quota`,** not surfaced to regular users via /feed banner. **DEVIATION from ROADMAP success #3** (`surface 429 visibly to that user`) — but logically consistent with service-level model: regular users have no actionable response to operator's quota state. ROADMAP success #3 in 3.0 reframes: "service-level throttle visibility = admin-only; per-user 429 surfacing for Reddit + Steam — Phase 3.1 / 3.2 scope".

Recorded fixture variant rejected — fixture maintenance burden + drift risk; mock is sufficient (live spike in Wave 0 Task #1 catches API-shape regressions).

- **D-NEW (All cron schedules internal) — pg-boss `boss.schedule()` inside scheduler container.** Operator does NOT add system-level crontab entries. Phase 3.0 schedules: `youtube.poll.active` `0 */6 * * *`, `youtube.poll.cold` `0 5 * * *`, `youtube.quota_reset` `0 0 * * *`, `purge.daily` `0 4 * * *`, `youtube.channel_context_backfill` (user-triggered queue, no cron). Healthcheck cron from Phase 1 (`internal.healthcheck` `*/5 * * * *`) continues. **Exception:** `backup.sh` stays system-level cron (Phase 02.2 D-25b — backup is host-level, not container-level). ## Decision Deviations Recorded During Discussion

These are explicit drifts from earlier locked artifacts that the user accepted on 2026-05-05 during /gsd:discuss-phase 03. Future agents must treat them as authoritative refinements.

- **DV-1 (PROJECT.md "Per-user API keys" Key Decision split per-platform).** Original blanket "per-user keys (YouTube/Reddit/Steam) distributes quotas, bounds blast radius" rule did not survive contact with YouTube's public-data + UX-friction reality (typical indie devs lack Google Cloud Console familiarity; data is identical across tenants regardless of who polls; Cloud Console setup is a real adoption barrier). Phase 3.0 Wave 0 commit splits the row in PROJECT.md "Key Decisions" table into three rows (YouTube service-level, Reddit per-user OAuth, Steam per-user per-publisher) and rewrites the "API quotas — why per-user keys matter" Context bullet to per-platform narrative. Phase 2 D-08 typed-per-kind `api_keys_*` schema is preserved for Reddit (Phase 3.1) and Steam (already shipped) but **NO `api_keys_youtube` table in Phase 3.0** — operator's keys live in env (`SERVICE_YOUTUBE_API_KEYS`); per-user override is Phase 6 trigger.

- **DV-2 (Polling tiers retire ROADMAP "Hot/Warm/Cold + Stale" 4-tier model).** Original ROADMAP success #1 specified "Hot — 30 min cadence first 24h", "Warm — every 6h", "Cold — daily", "Stale — no successful poll in >48h". User clarified during discussion that this is too aggressive for indie reality: "обычные видео, и через 28 дней перестаем обновлять просмотры". Revised to 3-tier + Frozen border: Active 0–24h (4×/день, every 6h) · Cold 1–28д (1×/day) · Frozen >28д (polling stops; refresh-now only). The "Stale" terminology is dropped entirely — its semantic ambiguity (when exactly does daily-polled cold become stale?) had no clean rule and surfaced Pitfall 7 risk; replaced with deterministic age-based Frozen + per-event `last_poll_status` for transient errors (`Unavailable · last seen Xd ago`).

- **DV-3 (ROADMAP success #3 reframes for service-level YouTube).** Original "When a per-user API key returns 429 / quota-exhausted, the affected job defers with backoff, the condition is surfaced visibly to that user" was written assuming per-user keys throughout. Service-level YouTube (DV-1) means the affected "user" is the operator, not regular users — they have no actionable response to operator's quota. Phase 3.0 reframes #3 to: "service-level throttle state visible only via `/admin/quota` (env allowlist gated); per-user 429 surfacing for Reddit + Steam keys lands in Phase 3.1 / 3.2." This is captured in D-16 + D-NEW Throttle Visibility decision.

- **DV-4 (Pitfall 17 retention strategy — defer rollup permanently).** RESEARCH.md and Phase 02.1 retention discussions assumed bounded snapshot growth required compaction strategy in Phase 6 (`raw 30d + daily roll-up`). The corrected Active/Cold/Frozen tier model (DV-2) makes snapshot growth asymptotically bounded per-video by construction: ~31 snapshots accumulated over 28 days, then growth stops. 1000 active videos/year ≈ 1.5MB. Pitfall 17 is not a real concern even at 100× scale. Phase 6 trigger removed from Phase 3.0 deferred-items.md.

- **DV-5 (Phase 02.2 D-11 quota model: events_per_day excludes auto-import).** Phase 02.2 D-11 implemented `withQuotaGuard('events_per_day')` against ALL event creation paths, including auto-import worker paths. Phase 3.0 surfaced that the 500/day cap is anti-abuse for human-driven creation; auto-import is system-driven and orthogonal to that intent. Refines D-11 by adding `source_id IS NULL` filter to the count query and bypassing `withQuotaGuard` entirely from auto-import worker. Closes Phase 02.2 PUTOFF "defer-not-throw auto-import" via the simpler exclusion approach.

- **DV-6 (Phase 02.2 AccountDeletedBanner Permanent-delete-now CTA activated).** Phase 02.2-04 shipped the CTA hidden with PUTOFF marker "purge endpoint ships in Phase 3 purge worker". Phase 3.0 lands the worker (D-NEW Purge worker) and activates the CTA. Type-DELETE confirm dialog gating preserved.

## Specific Ideas

- **"YouTube — задача сервиса. Это публичные данные."** The user's explicit reframing of the per-user-key model on 2026-05-05. Captured in DV-1; PROJECT.md "Key Decisions" + "API quotas" Context bullet rewritten to per-platform; ROADMAP reflects this in success #3 + #4.
- **"Hot — только первые сутки. Потом раз в день. После 28 дней — только refresh-now."** The user's lifecycle model that retired the original Hot/Warm/Cold + Stale 4-tier scheme. Captured in DV-2 + D-05; Frozen tier doubles as natural retention strategy (DV-4).
- **"Auto-import не должен учитываться в квоте."** events_per_day cap is anti-abuse for human-driven creates; auto-import is system-driven, orthogonal. Captured in DV-5 + D-NEW (events_per_day quota EXCLUDES auto-import).
- **"Мне как будто бы важно трекать ютуб каналы. Получается сравнить с другими видео на канале и понять его просмотры и медиану."** The user's median-context use case for blogger trailers. Captured in D-14 (channel context backfill on first paste; 2 quota units one-time per channel; Phase 4 chart median lives in `youtube_channel_metadata_cache` + `youtube_video_snapshots` rows).
- **"Админ панель — вайт лист, чтобы только нужные люди видели."** Operator visibility for service-level quota state without leaking to regular users. Captured in D-16 + DV-3; env-allowlist mechanism preserves AGENTS.md "no hard-coded admin allowlist" through env-configurability (same pattern as SUPPORT_EMAIL).
- **"Hard cap на дублирующий paste того же URL."** D-15 partial unique index closes the manual-paste dedup gap that Phase 2.1 schema left open (existing index covers only auto-import path).
- **"Несколько ключей в env? Сколько Google терпит?"** Multi-key support is technically straightforward (round-robin) but Google ToS limits practical fanout to ~2-3 keys per Cloud Console account before flagging quota circumvention. Paid tier (~$0.50/1000 unit) is the safer scale path. Captured in PollingBadge / quota throttle docs.
- **"Cron — сервис делает сам, не на хосте."** Reaffirmed pg-boss internal scheduler model; only `backup.sh` is host-level cron (Phase 02.2 D-25b). Captured in D-NEW (All cron schedules internal).
