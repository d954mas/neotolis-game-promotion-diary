# Phase 3.0: Polling Pipeline — Plumbing + YouTube — Research

**Researched:** 2026-05-05
**Domain:** pg-boss adaptive polling pipeline + YouTube Data API v3 service-level integration + soft-delete purge worker + admin allowlist gating
**Confidence:** HIGH (all load-bearing facts verified against locked artifacts + current Google/pg-boss docs; one Wave 0 LIVE spike defers actual quota math verification to plan execution time per CONTEXT D-02)

## Summary

Phase 3.0 lands the polling-pipeline plumbing (pg-boss adaptive queues + scheduler tier resolver + worker pool with SIGTERM-graceful drain) and the YouTube concrete `DataSourceAdapter` end-to-end, in the service-level quota model the user locked during /gsd:discuss-phase 03. The Phase 1 pg-boss bootstrap (`createBoss`/`stopBoss` 60s drain, `declareAllQueues`, dual `worker ready` / `scheduler ready` stdout-grep markers) is reused unchanged; Phase 3.0 simplifies the queue topology (POLL_HOT + POLL_WARM → POLL_ACTIVE per DV-2), adds three new domain queues (PURGE_DAILY, YOUTUBE_QUOTA_RESET, YOUTUBE_CHANNEL_CONTEXT_BACKFILL), and writes the worker handlers + scheduler cron registrations + adapter implementation that fill the Phase 2.1 STUB.

The locked stack (pg-boss 10.4.2, Drizzle 0.45.2, Hono 4.12.x, SvelteKit 2.58, Postgres 16) is preserved — Phase 3.0 introduces no new top-level deps. The single non-trivial tech inheritance hazard is **pg-boss 10's removal of `teamSize`/`teamConcurrency`** from `boss.work()` (v10 simplified to `batchSize` + multiple `boss.work()` calls); Phase 1's worker code already correctly uses the v10 array-handler shape, so the pattern is already in the codebase.

**Primary recommendation:** Treat the Wave 0 spike (live `videos.list` batched-call quota verification, CONTEXT D-02) as a hard gate — if the response cost differs from the documented 1 unit, the worker design re-pivots before any worker code lands. All other research findings are HIGH confidence and downstream-actionable.

#### Polling Tiers (POLL-01..05)

- **D-05 — Three tiers + Frozen border:** `Active 0–24h` (4×/день, every 6h) · `Cold 1–28д` (1×/day) · `Frozen >28д` (polling stops; refresh-now only). Boundaries computed from `events.occurred_at`, NOT `events.created_at`. The original ROADMAP "Hot/Warm/Cold + Stale" 4-tier model is RETIRED.

- **D-NEW (retention) — Keep all `youtube_video_snapshots` raw forever; no rollup.** Frozen tier IS the retention mechanism. ~1.5MB/year at 1000 active videos. Pitfall 17 retired by DV-4.

- **D-NEW (idempotency) — `polled_at` truncated to minute** in `youtube_video_snapshots` UNIQUE constraint. INSERT ON CONFLICT DO NOTHING idempotent across worker retries within the same minute.

- **D-NEW (PollingBadge copy):** `Hot · checked Xh ago` / `Cold · yesterday` / `Frozen · refresh to update` / `Unavailable · last seen Xd ago`. 5 Paraglide keys.

#### YouTube Adapter Scope (POLL-01..06, INGEST-02..04)

- **D-06 — Service-level YouTube quota model (DEVIATION from PROJECT.md "Per-user API keys" — for YouTube only).** One env var `SERVICE_YOUTUBE_API_KEYS` (comma-separated, 1+ keys). Worker round-robins; per-key quota state tracked in `youtube_service_quota_usage`. Shared snapshot cache by `video_id`.

- **D-07 — Snapshot cache shape: global `youtube_video_snapshots` table, no `user_id` column.** Public-data semantics. ESLint TENANT_TABLES allowlist extends with explicit comment `// public external data, no tenant scope`.

- **D-08 — Per-user YouTube key override DEFERRED to Phase 6.** No `/keys/youtube` UI in 3.0. No `api_keys_youtube` table in 3.0.

- **D-09 — Channel-registration backfill picker (5 presets, default 30):** When user registers a `youtube_channel` via `/sources/new`: `1 / 7 / 30 / 90 days / Everything` with `30` as default.

- **D-10 — Refresh-now: icon `[🔄]` on `<PollingBadge>` for any pollable event with `last_polled_at IS NOT NULL` OR Frozen.** Click → POST `/api/events/:id/refresh-poll` → enqueues to `poll.user` queue. Rate limit: 1 click per event per 5 minutes, persisted in `events.metadata.last_user_refresh_at`.

- **D-11 — Manual paste does NOT auto-create a `data_source` row.** Stats polling works on `events.external_id` directly.

- **D-12 — `not_found` / `private` / `auth_error` from `videos.list`: mark event off polling.** Worker writes `events.last_poll_status` accordingly + stops scheduling. PollingBadge renders `Unavailable · last seen Xd ago`. Audit `event.poll_failed` once on first failure.

- **D-13 — Service quota tracking: `youtube_service_quota_usage(date_pacific, api_key_id, estimated_units)` table.** Worker increments after each call (in same tx as snapshot insert). Scheduler reads at enqueue time. ≥80% pauses Cold + auto-import; ≥95% pauses Active too. Reset cron `0 0 * * *` (midnight Pacific). Audit `quota.service_throttled` once per threshold crossing per day.

- **D-14 — Channel context backfill (one-time per channel):** `playlistItems.list` last 50 videos (1 unit) + batched `videos.list` snapshot all 50 (1 unit) = 2 unit total. Caches channel meta + populates 50 video rows.

- **D-15 — Manual-paste dedup: partial unique index `events_user_kind_ext_active_unq ON events(user_id, kind, external_id) WHERE external_id IS NOT NULL AND deleted_at IS NULL`.** Service throws AppError 422 `duplicate_event`.

- **D-16 — Admin panel `/admin/*` gated on `c.var.userEmail in env.ADMIN_EMAIL_ALLOWLIST` (comma-separated, empty default).** Empty allowlist → all `/admin/*` returns 404. Phase 3.0 ships exactly one page: `/admin/quota`.

- **D-NEW (Shorts handling) — YouTube Shorts handled identically to regular videos.** Same endpoints. Worker stores `events.metadata.duration_seconds` and `events.metadata.is_short`.

- **D-NEW (Throttle visibility) — Service quota state visible ONLY in `/admin/quota`,** not surfaced to regular users. DEVIATION from ROADMAP success #3.

### Pattern 1: Tier Resolver (Single Source of Truth — Pitfall 7)

**What:** Pure function `resolveTier(occurredAt: Date, lastPollStatus: string | null, now: Date): 'active' | 'cold' | 'frozen' | 'unavailable'`. Single module imports both into scheduler enqueue path AND worker refresh-now path AND PollingBadge UI loader.

**When to use:** Every place that needs to decide "what tier is this event right now?" Replaces the entire ROADMAP "Hot/Warm/Cold + Stale" mental model with a deterministic boundary computation.

**Boundary rules** (from CONTEXT D-05 + D-12):

```typescript
// services/tier-resolver.ts
export type Tier = 'active' | 'cold' | 'frozen' | 'unavailable';

export function resolveTier(
  occurredAt: Date,
  lastPollStatus: string | null,
  now: Date = new Date(),
): Tier {
  // D-12: events whose last poll returned not_found / private / auth_error
  // are frozen-without-the-28d-wait. PollingBadge renders 'Unavailable …'.
  if (lastPollStatus === 'not_found' || lastPollStatus === 'private' || lastPollStatus === 'auth_error') {
    return 'unavailable';
  }
  const ageMs = now.getTime() - occurredAt.getTime();
  const ageDays = ageMs / 86_400_000;
  if (ageDays < 1) return 'active';   // 0–24h
  if (ageDays < 28) return 'cold';     // 1–28d
  return 'frozen';                     // >28d
}
```

### Pattern 2: Two-Phase Poll Job (Pitfall 5 — never hold tx across HTTP)

**What:** Worker job:
1. Phase A — short read tx: `SELECT id, user_id, occurred_at, external_id, metadata FROM events WHERE id = $1 AND deleted_at IS NULL` (no FOR UPDATE; pg-boss already holds the job lock)
2. Phase B — HTTP: round-robin pick a key from `SERVICE_YOUTUBE_API_KEYS` index, AbortController.timeout(30_000), `videos.list?id=v1,v2,...&part=snippet,statistics,contentDetails&key=<key>&quotaUser=<userId-hashed>`
3. Phase C — short write tx:
   ```sql
   BEGIN;
   INSERT INTO youtube_video_snapshots (video_id, polled_at, view_count, like_count, comment_count)
     VALUES ($1, date_trunc('minute', now()), $2, $3, $4)
     ON CONFLICT (video_id, polled_at, metric_key) DO NOTHING;
   UPDATE events SET last_polled_at = now(), last_poll_status = 'ok' WHERE id = $5;
   INSERT INTO youtube_service_quota_usage (date_pacific, api_key_id, estimated_units)
     VALUES ($6, $7, 1)
     ON CONFLICT (date_pacific, api_key_id) DO UPDATE SET estimated_units = youtube_service_quota_usage.estimated_units + EXCLUDED.estimated_units;
   COMMIT;
   ```
   Total tx duration <50ms.

**When to use:** Every external-API-touching worker job in this phase.

**pg-boss job lock note (verified):** pg-boss 10 uses `SKIP LOCKED` to acquire the job from `pgboss.job` table; the lock is held for the duration of the handler promise. This means:
- A 30s YouTube call DOES extend the job lock — but it does NOT hold a Drizzle row lock on `events`. The job-table lock contention is bounded to the queue's own row, never the application data.
- pg-boss's job-table partition + SKIP LOCKED means cross-job contention on the queue is non-existent at indie scale.

### Pattern 4: Service-Level Quota Round-Robin + Throttle Gate

**What:** Worker keeps `SERVICE_YOUTUBE_API_KEYS` (parsed from comma-separated env at boot) as an in-memory string array. Job N picks key index `N % keys.length`. Per-key spend tracked in `youtube_service_quota_usage(date_pacific, api_key_id, estimated_units)`. Scheduler reads usage at enqueue time:

```typescript
// scheduler/enqueue.ts (sketch)
const usage = await db.select().from(youtubeServiceQuotaUsage)
  .where(eq(youtubeServiceQuotaUsage.datePacific, todayPacific()));

const anyKeyAt95 = usage.some(u => u.estimatedUnits >= 9500);
const anyKeyAt80 = usage.some(u => u.estimatedUnits >= 8000);

if (anyKeyAt95) {
  // Pause everything but refresh-now
  return;
}
if (anyKeyAt80) {
  // Pause Cold + auto-import; Active continues
  enqueueOnly('active');
  return;
}
enqueueAll();
```

**Audit transition logic** (idempotent — once per threshold per day):

```typescript
// Re-read previous threshold state from a 'youtube_quota_threshold_state' tiny table
// OR derive from audit_log "is there a quota.service_throttled with metadata.threshold=80
// and date=today?". The latter avoids a new table; planner picks.
```

`quota.service_throttled` audit row writes ONLY on transition (80% crossed first time today, 95% crossed first time today). Subsequent ticks within same threshold band do not re-emit.

**`quotaUser` parameter** (verified from Google docs): the standard query parameter `quotaUser=<opaque-string-≤40-chars>` lets server-side apps track per-end-user quota beyond the per-key envelope. **For Phase 3.0**: pass `quotaUser=hash(events.userId)` (sha256 → first 16 hex chars). Effect: Google internally bills the call to that synthetic user, distributing fairness across our tenants. Practical impact at indie scale: low (operator's 10k/day envelope is the binding constraint, not per-user fanout). Recommended **for documentation completeness — set it; don't rely on it**.

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Cron scheduling | A node-cron / setInterval poll loop in scheduler | `boss.schedule(queueName, cron5field, data?, { tz?: 'America/Los_Angeles' })` | pg-boss 10 has built-in cron with distributed lock (verified) — single-instance leadership election handled by pg-boss's `trySetCronTimeCommand` + 60s singleton (deepwiki.com/timgit/pg-boss/10.1-cron-based-scheduling). | Job retry with exponential backoff | Manual try/catch wrapper | pg-boss queue-level policy: `boss.createQueue(name, { policy: 'standard', retryLimit: 5, retryBackoff: true, retryDelay: 30 })` | Standard pattern; integrated with DLQ; no retry-loop bugs. |

## Common Pitfalls

### Pitfall A: pg-boss v10 `teamSize`/`teamConcurrency` no longer exists

**What goes wrong:** A planner assumes pg-boss exposes `teamSize` (per pre-2024 patterns / blog posts) and writes `boss.work(name, { teamSize: 4 }, handler)`. v10 silently ignores unknown options; concurrency stays at default 1; throughput is 4× lower than expected.

**Why it happens:** pg-boss 10.0 (released ~2024) explicitly REMOVED these options. v9 docs and blog posts predate the change and rank in search.

**How to avoid:**
- Use `batchSize` for in-handler batching (handler always gets array of jobs).
- Use multiple `boss.work()` calls per queue for true concurrency, OR rely on pg-boss's internal worker pool (controlled via `pollingIntervalSeconds` + queue-level `policy`).
- See verified release notes: https://github.com/timgit/pg-boss/releases/tag/10.0.0

**Warning signs:** worker process exists, jobs are present in the queue, but only 1 is processed at a time. Check with `SELECT count(*) FROM pgboss.job WHERE state = 'active' GROUP BY name`.

### Pitfall B: Phase 1 worker code uses array-handler shape — DO NOT regress

**What goes wrong:** A "modernization" PR rewrites the Phase 1 healthcheck handler from `async (jobs) => { for (const job of jobs) ... }` to `async (job) => ...`. v10 invokes handler with array; the destructuring fails or processes only `jobs[0]`.

**How to avoid:** Phase 1 worker (`src/worker/index.ts:46`) ALREADY USES the v10-correct shape. Reuse the pattern verbatim for new poll handlers:

```typescript
await boss.work(QUEUES.POLL_ACTIVE, { batchSize: 4 }, async (jobs) => {
  for (const job of jobs) {
    await handlePollActive(job);
  }
});
```

### Pitfall C: YouTube `videos.list` `part=` rumor

**What goes wrong:** Persistent online claim that `part=snippet,statistics,contentDetails` multiplies the call cost (1 unit per part). Operator paranoid and skips needed parts.

**Verified fact (Google official docs, 2026-05-05):** `videos.list` is **1 unit per call**, regardless of `part=` values, regardless of how many video IDs are batched (max 50). The `part=` parameter is FREE; it controls response shape, not cost.

**Source:** https://developers.google.com/youtube/v3/docs/videos/list — "A call to this method has a quota cost of 1 unit." Cross-verified against https://developers.google.com/youtube/v3/determine_quota_cost ("videos.list: 1 point").

**Recommendation:** Always request `part=snippet,statistics,contentDetails` in one call. snippet gives `title`, `publishedAt`; statistics gives view/like/comment counts; contentDetails gives `duration` (needed for D-NEW Shorts handling). One call covers everything Phase 3.0 needs.

### Pitfall D: YouTube quota reset is midnight Pacific, NOT UTC

**What goes wrong:** Operator schedules `youtube.quota_reset` cron at `0 0 * * *` UTC and resets the counter at the wrong moment. Phase 3.0 quota throttle gates fire 7-8 hours late.

**Verified fact:** "Daily quotas reset at midnight Pacific Time (PT)." (Google official docs).

**Recommendation:** pg-boss `boss.schedule(QUEUES.YOUTUBE_QUOTA_RESET, '0 0 * * *', null, { tz: 'America/Los_Angeles' })`. Verified — pg-boss 10 supports `tz` option in schedule (deepwiki.com/timgit/pg-boss/10.1-cron-based-scheduling). For all OTHER schedules (`youtube.poll.active`, `youtube.poll.cold`, `purge.daily`), planner picks tz: pg-boss default (UTC) is fine for those, OR follow operator preference. The 4 AM PT for `purge.daily` is from CONTEXT — set tz=`America/Los_Angeles`.

### Pitfall E: Admin route allowlist is parsed at boot, not on every request

**What goes wrong:** Operator adds an email to `ADMIN_EMAIL_ALLOWLIST` env, expects immediate effect, doesn't restart container, files a bug. The middleware caches the parsed Set at module load time.

**Recommendation:** Document this clearly in `.env.example`:
```
# Comma-separated list of admin user emails (empty default = all /admin/* returns 404).
# Changes require container restart.
ADMIN_EMAIL_ALLOWLIST=
```

Boot-time parse is the simpler, faster, and security-positive choice (no per-request file I/O). Phase 6 expansion (per-user QUOTA-01 dashboards) may add hot-reload via SIGHUP — out of scope for 3.0.

### Pitfall F: Manual paste of duplicate URL — pre-Phase 3.0 dedup gap

**What goes wrong:** Phase 2.1 schema has `events_user_kind_source_ext_unq WHERE source_id IS NOT NULL AND external_id IS NOT NULL` — but this only covers auto-imported events. A user pasting `youtube.com/watch?v=abc` twice manually (source_id=NULL on both) inserts two rows.

**Verified:** events.ts schema lines 113-115 confirm.

**Mitigation (CONTEXT D-15):** Wave 0 baseline migration adds:
```sql
CREATE UNIQUE INDEX events_user_kind_ext_active_unq
  ON events(user_id, kind, external_id)
  WHERE external_id IS NOT NULL AND deleted_at IS NULL;
```

Service throws `AppError(422, 'duplicate_event')` on Postgres 23505. Path: `services/events.ts:createEvent` already has Phase 2.1 dedup-handling pattern for the auto-import case (Plan 02.1-29 Steam listings precedent — pre-INSERT lookup + race-window catch); extend with the new constraint name.

### Pitfall G: pg-boss createQueue idempotency + dropped queues

**What goes wrong:** Phase 3.0 drops `POLL_WARM` (DV-2 collapse). The Phase 1 `declareAllQueues()` no longer references it. But pg-boss already declared it on a prior boot — the row in `pgboss.queue` persists.

**Mitigation:** Wave 0 baseline migration cleanup:
```sql
DELETE FROM pgboss.queue WHERE name IN ('poll.warm', 'poll.hot');
-- Then declareAllQueues() on next boot creates 'poll.active' fresh.
```

Note: 'poll.hot' is renamed to 'poll.active' — the old name's queue rows must be drained or dropped to avoid stale jobs. Since Phase 1 ran NO real poll jobs, the queue is empty; safe to DELETE FROM pgboss.queue WHERE name = 'poll.hot' as well.

### Pitfall H: PollingBadge reads occurredAt from event row — verify type round-trip

**What goes wrong:** The Phase 2.1 PollingBadge accepts `lastPolledAt: Date | string | null`. Phase 3.0 also needs `occurredAt: Date | string` for tier resolution. SvelteKit serialization sends Dates as ISO strings over the wire; client coerces.

**Mitigation:** Component prop type `EventForBadge = { kind, occurredAt: Date | string, lastPolledAt: Date | string | null, lastPollStatus: string | null, lastUserRefreshAt: Date | string | null }`. Convert on entry: `const occurredDate = typeof event.occurredAt === 'string' ? new Date(event.occurredAt) : event.occurredAt`. tier-resolver expects `Date`, not `Date | string`.

## Code Examples

### Example 1: YouTube videos.list batched call (verified 1 unit per call)

```typescript
// src/lib/server/integrations/youtube-channel-adapter.ts (Wave 1 — replaces Phase 2.1 STUB)
import { z } from 'zod';
import { env } from '../config/env.js';
import { createHash } from 'node:crypto';
import type { DataSourceAdapter, EventRow, StatsSnapshot, DataSourceRow } from './data-source-adapter.js';

const VIDEOS_LIST_RESPONSE = z.object({
  kind: z.literal('youtube#videoListResponse'),
  items: z.array(z.object({
    id: z.string(),
    snippet: z.object({
      publishedAt: z.string(),
      title: z.string(),
      channelId: z.string(),
    }).optional(),
    statistics: z.object({
      viewCount: z.string().optional(),
      likeCount: z.string().optional(),
      commentCount: z.string().optional(),
    }).optional(),
    contentDetails: z.object({
      duration: z.string(), // ISO 8601 duration "PT4M13S"
    }).optional(),
  })),
});

const YOUTUBE_API_BASE = process.env.YOUTUBE_API_BASE_URL ?? 'https://www.googleapis.com/youtube/v3';
// NOTE: this is the ONE legitimate process.env read outside config/env.ts during the
// smoke override — production code path goes through env.ts. Planner: route through
// env.ts to keep AGENTS.md AP-6 invariant clean.

export async function pollYoutubeVideoStats(
  videoIds: string[], // up to 50 — batched per call (1 unit total)
  apiKey: string,
  endUserIdHash: string, // hash(events.userId) for quotaUser fairness
): Promise<StatsSnapshot[]> {
  if (videoIds.length === 0) return [];
  if (videoIds.length > 50) throw new Error('videos.list batch limit is 50');

  const url = new URL(`${YOUTUBE_API_BASE}/videos`);
  url.searchParams.set('id', videoIds.join(','));
  url.searchParams.set('part', 'snippet,statistics,contentDetails');
  url.searchParams.set('key', apiKey);
  url.searchParams.set('quotaUser', endUserIdHash);

  const ac = new AbortController();
  const timeout = setTimeout(() => ac.abort(), 30_000);
  try {
    const resp = await fetch(url, { signal: ac.signal });
    if (!resp.ok) {
      // Distinguish 403 quotaExceeded vs 403 forbidden — Pitfall 8
      if (resp.status === 403) {
        const body = await resp.json() as { error?: { errors?: Array<{ reason?: string }> } };
        const reason = body.error?.errors?.[0]?.reason;
        if (reason === 'quotaExceeded') {
          return videoIds.map(id => ({ polledAt: new Date(), metrics: {}, status: 'rate_limited' as const }));
        }
        return videoIds.map(id => ({ polledAt: new Date(), metrics: {}, status: 'auth_error' as const }));
      }
      if (resp.status === 404) {
        return videoIds.map(id => ({ polledAt: new Date(), metrics: {}, status: 'not_found' as const }));
      }
      throw new Error(`videos.list failed: ${resp.status}`);
    }
    const json = VIDEOS_LIST_RESPONSE.parse(await resp.json());
    const now = new Date();
    return videoIds.map(videoId => {
      const item = json.items.find(i => i.id === videoId);
      if (!item) return { polledAt: now, metrics: {}, status: 'not_found' as const };
      // YouTube returns view counts as strings; coerce.
      return {
        polledAt: now,
        metrics: {
          view_count: Number(item.statistics?.viewCount ?? 0),
          like_count: Number(item.statistics?.likeCount ?? 0),
          comment_count: Number(item.statistics?.commentCount ?? 0),
        },
        status: 'ok' as const,
      };
    });
  } finally {
    clearTimeout(timeout);
  }
}

export function hashUserIdForQuotaUser(userId: string): string {
  // 16 hex chars — well below 40-char quotaUser limit.
  return createHash('sha256').update(userId).digest('hex').slice(0, 16);
}
```

### Example 2: Idempotent snapshot writer

```typescript
// src/lib/server/services/youtube-snapshot-writer.ts
import { sql } from 'drizzle-orm';
import { db } from '../db/client.js';
import { youtubeVideoSnapshots } from '../db/schema/youtube-video-snapshots.js';
import { events } from '../db/schema/events.js';
import { youtubeServiceQuotaUsage } from '../db/schema/youtube-service-quota-usage.js';

export async function writeSnapshot(args: {
  videoId: string;
  eventId: string;
  metrics: { view_count: number; like_count: number; comment_count: number };
  apiKeyId: string;     // index/identifier of the operator key used
  unitsUsed: number;    // 1 for videos.list batched
  status: 'ok' | 'not_found' | 'private' | 'auth_error' | 'rate_limited';
}): Promise<void> {
  await db.transaction(async (tx) => {
    if (args.status === 'ok') {
      // Idempotent INSERT ON CONFLICT DO NOTHING — within-the-minute retries are no-ops.
      await tx.insert(youtubeVideoSnapshots).values({
        videoId: args.videoId,
        polledAt: sql`date_trunc('minute', now())`,
        viewCount: args.metrics.view_count,
        likeCount: args.metrics.like_count,
        commentCount: args.metrics.comment_count,
      }).onConflictDoNothing();
    }

    await tx.update(events)
      .set({
        lastPolledAt: new Date(),
        lastPollStatus: args.status,
      })
      .where(/* eq(events.id, args.eventId) — see ESLint rule note: eventId scope is the worker context */);
    // ESLint tenant-scope rule: events is tenant-owned; the planner should structure
    // the worker call site to pass userId from the loaded event row and add
    // eq(events.userId, userId) — matching Phase 2.1 worker pattern.

    // Quota counter — UPSERT pattern. Postgres ON CONFLICT (date_pacific, api_key_id) DO UPDATE.
    await tx.insert(youtubeServiceQuotaUsage).values({
      datePacific: todayPacific(), // helper: format as 'YYYY-MM-DD' in America/Los_Angeles
      apiKeyId: args.apiKeyId,
      estimatedUnits: args.unitsUsed,
    }).onConflictDoUpdate({
      target: [youtubeServiceQuotaUsage.datePacific, youtubeServiceQuotaUsage.apiKeyId],
      set: {
        estimatedUnits: sql`${youtubeServiceQuotaUsage.estimatedUnits} + ${args.unitsUsed}`,
      },
    });
  });
}
```

2. **`youtube_channel_metadata_cache` — own table vs. jsonb in `data_sources.metadata`?** (CONTEXT Discretion)
   - What we know: Cache holds channel-level public data (channel_id, uploads_playlist_id, channel_title, last_backfill_at). It's NOT user-scoped — same channel_id seen by 50 users gets the same metadata.
   - What's unclear: do we store a row per channel-paste-event, or merge into data_sources.metadata jsonb (per-tenant)?
   - Recommendation: **Own table** (planner may revisit). Public-data semantics matches `youtube_video_snapshots`'s no-user_id design — keeps the "shared cache" mental model uniform. ESLint TENANT_TABLES allowlist same comment.

3. **`purgeAccount(userId)` — single tx vs cascade chain?** (CONTEXT Discretion)
   - What we know: Phase 02.2 `softDeleteAccount` uses a single tx with explicit cascade chain (user → games → game_steam_listings → data_sources → events → api_keys_steam + session). Pattern proven and reviewed.
   - What's unclear: `purge` is destructive (DELETE not UPDATE) and has different idempotency (re-running on a partially-purged user must not error).
   - Recommendation: **Single tx, idempotent DELETE chains** (DELETE WHERE …, deletedAt IS NOT NULL AND deletedAt < ts → if no rows match, no-op, no error). Audit `purge.completed` writes OUTSIDE the tx (Phase 02.2 pool-deadlock-safe pattern). Planner picks exact ordering — must respect FK constraints (events refs sources; sources ref users; user is last).

4. **Audit `purge.completed` tenant scope — operator's userId, the purged userId, or per-purged user one row each?** (CONTEXT Discretion + Pitfall 19)
   - What we know: AGENTS.md invariant 4 says audit log is "tenant-relative" — cursors pagination. Pitfall 19 says cross-tenant audit metadata is forbidden.
   - What's unclear: when the cron job purges 5 users in one tick, does it write 1 audit row (under operator's user_id) or 5 rows (one per purged user)?
   - Recommendation: **5 rows, each scoped to the purged user's user_id**, with `metadata.row_counts: { games: N, events: N, ... }` for that user only. This preserves the per-tenant cursor invariant and avoids the operator's audit log filling up. The user is gone but their final audit row remains (audit is INSERT-only, never deleted by purge — Phase 02.2 D-15 already preserves this). Admin /admin/quota can `SELECT … FROM audit_log WHERE action = 'purge.completed' ORDER BY occurred_at DESC LIMIT 50` cross-tenant — admin allowlist is the gate, NOT user_id matching.

5. **Concrete Paraglide message keys for PollingBadge variants.** (CONTEXT Discretion)
