# Phase 03.0 Plan 05: Purge Account Service Summary

**purgeAccount(userId, opts) ships the third leg of the soft-delete tripod — single-tx FK-ordered hard-delete cascade with audit OUTSIDE the tx, idempotent on re-run, and a forward-only migration that drops the audit_log → user FK so the purge.completed audit row survives the user delete (Open Question 4 / GDPR Art. 17 60-day-grace).**

## Accomplishments

- **`purgeAccount(userId, opts)` lives at `src/lib/server/services/purge-account.ts`** — one tx, eight cascade DELETE steps in FK-respecting order, audit `purge.completed` written OUTSIDE the tx with `metadata.row_counts: { apiKeysSteam, events, eventGames, gameSteamListings, dataSources, games, sessions, user }`. Eligibility gate consults `env.RETENTION_DAYS` (default 60) and skips when `user.deletedAt` is null OR within the grace window. `opts.ignoreRetention=true` bypasses the gate for the Permanent-delete-now CTA path.
- **`listPurgeEligibleUsers(now?)` helper** for Plan 09's `purge.daily` cron — returns user_ids whose `deletedAt < now - RETENTION_DAYS`. Active users (deletedAt IS NULL) excluded by construction (the `isNotNull` predicate is part of the WHERE).
- **Migration 0011 drops `audit_log.user_id → user(id)` FK** — without this the prior FK had `ON DELETE CASCADE` and would have garbage-collected the `purge.completed` audit row at the moment of `DELETE FROM "user" WHERE id = ?`. Dropping the FK makes audit_log.user_id a plain text column whose value outlives its referent. AGENTS.md §4 (audit INSERT-only) is preserved for this verb. P19 cursor invariant unchanged — the `(user_id, created_at)` and `(user_id, action, created_at)` indexes still support tenant-relative pagination only.
- **Re-exports from `services/account.ts`** so `import { purgeAccount } from '../services/account.js'` works alongside `softDeleteAccount` / `restoreAccount` / `exportAccountJson`. Plan 08 (route layer) and Plan 09 (worker layer) pick whichever import style matches the surrounding code.
- **10 service-layer integration tests covering** eligibility (deletedAt null / 30d / past retention), CTA bypass, idempotency, audit row contract (scoped to purged user_id with full row_counts metadata), cross-tenant audit-log integrity, cross-tenant data integrity, cascade order (M:N event_games junction with multi-game attachment), `listPurgeEligibleUsers` filtering by retention cutoff. The 4 it.skip route-layer stubs from Plan 02 are preserved verbatim for Plan 03.0-08.

## Decisions Made

- **Audit-log FK drop in a SEPARATE migration (0011), not amend 0010.** Plan 01's migration is already merged; amending it would violate forward-only. Write-before-tx (the alternative the plan listed) leaves a phantom audit row if the cascade tx rolls back, defeating idempotency. The migration is one DDL line plus an IF EXISTS guard; pnpm db:check zero drift verified.
- **Cascade order: api_keys_steam → event_games → events → game_steam_listings → data_sources → games → session → user.** Test 8 exercises this with a fully-loaded fixture (M:N event attached to two games, two listings, a source, a Steam key). The order matters because event_games has FKs to events.id (ON DELETE CASCADE) and games.id (ON DELETE CASCADE) — the row-count probe (`.returning({ eventId })`) only sees rows we ourselves DELETE'd, not cascade-collateral, so deleting event_games first gives the audit metadata accurate counts.
- **`PurgeOptions.ipAddress` with `"system"` default.** writeAudit requires `ipAddress` (P19 — real IPs from day one) but the cron worker has no request context. The default makes the cron-side audit row legibly say `"system"` rather than synthesising a fake IP. The CTA route (Plan 08) will pass the user's real IP via `c.var.ipAddress`. Pino redact paths cover the field name regardless.
- **Better Auth `account` table delete is implicit (FK cascade), not explicit.** Schema declares `account.userId` with `onDelete: "cascade"`, so the `user` DELETE in step 8 takes the OAuth tokens with it. Adding an explicit `tx.delete(account)` step would be redundant + obscure the FK semantics. PurgeRowCounts therefore has 8 fields, not 9 — the missing one is `accounts` (cascade-collateral, count invisible).
- **Re-export from `services/account.ts` rather than create a `services/index.ts` barrel.** The codebase has no services barrel; account.ts is the natural home because it already houses the soft-delete + restore + export trio. The re-export keeps the import surface small without committing the project to a barrel pattern.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 — Blocking] audit_log → user FK had ON DELETE CASCADE; required a new migration before the service could ship correctly**

- **Found during:** Task 1 (schema inspection — `src/lib/server/db/schema/audit-log.ts` line 43 declared `references(() => user.id, { onDelete: "cascade" })`; the 0010 snapshot confirmed the FK was active in production).
- **Issue:** Both options the plan listed for the audit-row write order broke AGENTS.md §4 (audit INSERT-only):
  1. Write audit BEFORE the cascade tx → the cascade DELETEs the audit row (FK was ON DELETE CASCADE). The purge.completed verb effectively never reaches audit_log.
  2. Write audit AFTER the cascade tx → the FK rejects the INSERT (the user row no longer exists). writeAudit catches and logs the error → silent audit drop.
- **Fix:** Wrote a third option that the plan's "Audit-log FK consideration" block listed: **drop the FK in a new forward-only migration**. Created `drizzle/0011_drop_audit_log_user_fk.sql` (1 DDL statement + IF EXISTS guard + 30-line rationale block). Updated `src/lib/server/db/schema/audit-log.ts` to remove the `references(...)` clause and document the new contract. Generated `drizzle/meta/0011_snapshot.json` derived from 0010 with the FK removed. Appended `_journal.json` idx=11 entry.
- **Files modified:** drizzle/0011_drop_audit_log_user_fk.sql, drizzle/meta/0011_snapshot.json, drizzle/meta/_journal.json, src/lib/server/db/schema/audit-log.ts.
